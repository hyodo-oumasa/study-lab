# Associate 分野 2：出力の評価と検証

[Associate – Foundations](./associate) の出題分野 2「出力の評価と検証」（Output Evaluation and Validation）を、試験ガイドの項目ごとに見ます。比重は 21% で、7 つの分野の中でいちばん大きい分野です。

## この分野の項目

試験ガイドは、この分野について 6 つの項目を挙げています。分野の名前と項目は、日本語版の試験ガイド（Version 1.0）の言い方に合わせ、短くまとめました。

| 番号 | 項目 |
|---|---|
| 1 | 出力の正確性と網羅性を評価する |
| 2 | ハルシネーション、不整合、バイアスを特定する |
| 3 | ファクトチェックと検証の手法を使う |
| 4 | 人間によるレビューや、追加の検証が必要な場面を判断する |
| 5 | 想定する読み手に合わせて、出力を編集、調整、改良、比較する |
| 6 | 情報を整理、選別し、出力の形式（アーティファクト、インライン、構造化データ）を選ぶ |

この分野で使う言葉です。

| 日本語 | 英語 | 意味 |
|---|---|---|
| 正確性 | accuracy | 書かれている内容が、事実や資料と合っていること |
| 網羅性 | completeness | 必要な内容が、抜けずに入っていること |
| ハルシネーション | hallucination | AI が、事実でない内容を、もっともらしく作ってしまうこと |
| 不整合 | inconsistency | 同じ出力の中や、資料との間で、内容が食い違っていること |
| バイアス | bias | 見方や表現が、一方に偏っていること |
| ファクトチェック | fact-checking | 出力の中の事実を、元の資料や信頼できる情報源で確かめること |
| 引用 | citation | 出力の根拠として、資料の場所や文を示すこと |
| アーティファクト | artifact | claude.ai で、会話とは別の画面に表示される成果物（文書、コード、図など） |
| インライン | inline | 会話の中に、そのまま答えを書くこと |
| 構造化データ | structured data | 表、JSON、CSV のように、決まった形に整えたデータ |

## 項目 1　出力の正確性と網羅性を評価する

- **要点**
  - 評価は 2 つに分けて考える。**正確性**は「書かれていることが正しいか」、**網羅性**は「書かれるべきことが抜けていないか」。
  - 網羅性は、出力だけを読んでも分からない。依頼の内容や元の資料と照らし合わせて、「何が入っているべきか」を先に決めておく。
  - Claude は、新しい出来事について、最新の情報を持っていないことがある。最新の情報が要る作業では、特に確かめる。
  - **PDF のページ数**で、読まれる中身が変わる。100 ページまでの PDF は、図やグラフも読む。101〜1,000 ページの PDF は、取り出した文字だけを読み、図やグラフは読まない。長い PDF の要約では、図やグラフの中にしかない情報が入っているかを確かめる。
- **公式ドキュメント**
  - ヘルプセンターの「Claude is providing incorrect or misleading responses. What's going on?」。最新の情報がないことと、もっともらしい誤りを作ることが、誤りの例として挙げられている。
  - ヘルプセンターの「Upload files to Claude」。PDF のページ数と、図を読むかどうか。
- **試験での見分け方**：「正しいことしか書かれていないが、大事な点が抜けている」出力は、正確でも網羅的ではない。選択肢で「正確性を確かめる」と「網羅性を確かめる」が分かれていたら、場面で問われているのはどちらかを見る。
- **紛らわしいもの**：網羅性は「長いほどよい」ではない。依頼に要らない内容が多いことは、網羅性の高さではなく、項目 6 の「選別」の問題。

## 項目 2　ハルシネーション、不整合、バイアスを特定する

- **要点**
  - **ハルシネーション**：もっともらしい引用や主張が、事実に基づいていないことがある。数字、固有名詞、日付、引用、出典は、特に疑う。
  - **不整合**：出力の前半と後半、表と本文、資料と要約の間で、内容が食い違っていないかを見る。同じ依頼を何回か出して答えを比べ、答えが毎回違う部分は、ハルシネーションの疑いがある。
  - **バイアス**：一方の見方だけを取り上げていないか、特定の人や集団について決めつけた表現がないかを見る。
    - 偏りは、プロンプト、前提の置き方、文章が作られるときの根っこのパターンから入ることがある。採用、評価、特定のグループへの連絡など、人に直接関わる出力では、人を公平に扱っているか、前提の置き方が結果を偏らせていないかを確かめる（準備コース「倫理的な観点：バイアス、公正性、透明性」。くわしくは [分野 6](./associate-6-governance) の項目 4）。
- **公式ドキュメント**
  - ヘルプセンターの「Claude is providing incorrect or misleading responses. What's going on?」。権威がありそうに聞こえるが、事実に基づかない引用や主張を作ることがある、とされている。
  - 開発者向けドキュメントの「Reduce hallucinations」。同じプロンプトを何回か実行して出力を比べ、食い違いからハルシネーションに気づく方法が「Best-of-N verification」として紹介されている。
- **試験での見分け方**：「自信のある書き方をしているから正しい」とは考えない。書き方の自信と、内容の正しさは別のもの。
- **紛らわしいもの**：何回か出して答えが毎回同じでも、正しいとは限らない。答えの食い違いはハルシネーションに気づく手がかりで、正しさは元の資料や信頼できる情報源で確かめる（項目 3）。

## 項目 3　ファクトチェックと検証の手法を使う

- **要点**
  - 確かめる相手は、**会話の外**にあるもの（元の資料、情報源、テスト、ほかの人）。Claude の出力を、形を変えて Claude に確かめさせても、確かめたことにならない。
  - **元の資料と照らし合わせる**：資料を渡した作業なら、主張ごとに、資料のどこに書かれているかを確かめる。Claude に「主張ごとに、根拠になる資料の文を引用させる」「根拠の文が見つからない主張は消させる」こともできる。
  - **引用を見る**：ウェブ検索を使った答えには、引用と出典のリンクが付く。リンク先の元のページを読み、Claude の要約が元の内容と合っているかを確かめる。
  - **「分からない」と言ってよいと伝える**：分からないときは「分からない」と答えてよい、と先に伝えると、事実でない内容が減る。
  - **渡した資料だけを使わせる**：一般的な知識ではなく、渡した資料だけを使うように指示する。
- **公式ドキュメント**
  - 「Reduce hallucinations」。「分からない」と言ってよいと伝える、引用で根拠を示させる、渡した資料だけを使わせる、などの方法が挙げられている。ただし、どの方法もハルシネーションを完全にはなくせない、と書かれている。
  - ヘルプセンターの「Enable and use web search」。ウェブ検索の答えには引用が付き、自分で出典を確かめられる。大事な判断には、信頼できる情報源を使うよう勧めている。
  - Claude Academy の「Anthropic Education Report: How people check Claude's work」。人が Claude の仕事を確かめるときは、主に会話の外のもの（情報源、資料、テスト、ほかの人、別の AI）と照らし合わせていた。
- **試験での見分け方**：「Claude にもう一度聞いて確かめる」だけでは、検証として弱い。元の資料や、信頼できる情報源と照らし合わせる選択肢を選ぶ。選択肢が最後に何を見て判断するのかを確かめる。Claude の報告や答えで終わるなら、まだ Claude の出力のまま。
- **紛らわしいもの**
  - 引用が付いていても、要約が元のページの内容と合っているとは限らない。ヘルプセンターも、元のページには要約に入っていない文脈や詳しい内容があることがある、としている。
  - **引用させる方法は、資料を渡したときや、検索したときに使う**。資料も検索もなく、記憶から答えた返事に、あとから引用を付けさせても、確かめたことにならない。Claude は、権威がありそうでも事実に基づかない引用を出すことがある（ヘルプセンター）。
  - **リサーチ**は、多くの情報源を調べて報告を作る。ただし、報告は Claude のまとめなので、大事な判断では、引用元を自分で確かめる。拡張思考は考える量を増やすが、外の事実を確かめはしない。

## 項目 4　人間によるレビューや、追加の検証が必要な場面を判断する

- **要点**
  - 間違えたときの影響が大きい内容は、人間が確かめる。たとえば、法律、医療、お金、採用など、人の生活や権利に関わる判断。
  - Claude を唯一の情報源にしない。大事な情報は、ほかの情報源と照らし合わせる。
  - 確かめるのは、元の情報を判断できる人。専門家に限らず、利用者自身でもよい。ヘルプセンターも、影響の大きい助言は利用者が注意して確かめるよう書いている。
  - 確かめるときのいちばんの壁は、その分野の知識がないこと。公式のレポートは、自分で知識を付ける方法と、確かめを頼める詳しい人を見つけておく方法の両方を挙げている。
- **出力のトリアージ**：**トリアージ**は、もとは医療で、手当ての優先度を決めること。ここでは、Claude の出力ごとに、どこまで確かめてから使うかを分けることを指す。準備コースは、次の 3 つに分けている。

| 分け方 | 当てはまる出力 | すること |
|---|---|---|
| そのまま使用可能 | 間違えても影響が小さい。社内向けで、下書きと分かっている | 軽く手を入れて使う（弱い案を削るなど） |
| 修正が必要 | 直し方の決まった欠陥がある（合計が各項目と合わない、統計に出典がない など） | 欠陥を直してから使う（コード実行で計算し直す、確かめられる出典を求める、信頼できる情報源と照らし合わせる） |
| 人による判断が必要 | 重大性が高い。外部（規制当局など）に出す、出したら取り消せない | 整って見えても、専門家に確かめてもらう |

  - **重大性**（間違えたときの影響の大きさ）を決めるのは、読み手（社内か外部か）、取り消せるかどうか、下書きか完成品か。
  - **見た目の質とリスクは、別の軸**。いちばん整って見える出力が、いちばん重い確認を要することがある。雑に見える出力が、軽い確認で済むこともある。
- **公式ドキュメント**
  - ヘルプセンターの「Claude is providing incorrect or misleading responses. What's going on?」。影響の大きい助言は、行動する前に注意して確かめるよう勧めている。
  - 「Reduce hallucinations」。大事な情報は、特に影響の大きい判断では、いつも確かめるよう書かれている。
  - Anthropic の利用規約（Usage Policy。2026 年 11 月 12 日に発効する版）。影響の大きい使い方では、資格のある人が確かめることが求められている。詳しくは、[分野 6「ガバナンス、リスク、責任ある利用」](./associate-6-governance)のページで扱う。
  - Claude Academy の「Anthropic Education Report: How people check Claude's work」。分野の知識がないことが、確かめるときのいちばんの壁だった。
- **公式の教材**：準備コースの演習「出力セットのトリアージ」。重大性と見た目の質を分けて判断する練習。
- **試験での見分け方**
  - 影響の大きさで判断する。社内メモの言い回しを整える作業と、顧客への法律の説明を作る作業では、必要な確認の重さが違う。
  - 「抜粋して確かめたら正確だった」「よく整っている」とあっても、外部に出して取り消せないものなら、人による判断が必要。
  - 「修正が必要」と「人による判断が必要」の分かれ目：欠陥が見つかっていて、直し方が決まっているなら「修正が必要」。欠陥が見つからなくても、重大性が高ければ「人による判断が必要」。
- **紛らわしいもの**
  - 「AI を使わない」は、多くの場合、正解ではない。Claude を使ったうえで、人が確かめる手順を入れる選択肢が正解になりやすい。
  - ブレインストーミングで、よい案と平凡な案が混ざっているのは、欠陥ではない。案を広く出すという目的どおりの出力で、弱い案を削れば使える。

## 項目 5　想定する読み手に合わせて、出力を編集、調整、改良、比較する

- **要点**
  - 同じ内容でも、読み手によって、言葉の難しさ、長さ、詳しさ、書き方を変える。たとえば、経営層には結論を先に、現場の担当者には手順を細かく書く。
  - 一度で完成させようとせず、出力を読んで、足りないところを指示して直させる。
  - 何通りかの案を出させて比べ、よいところを選ぶ。
  - **直すのは、指摘されたところだけ**。ほかの部分が承認済みなら、全体を書き直したり、新しいチャットで作り直したりしない。承認済みの言い回しまで変わり、全体をもう一度確かめることになる。直したあとは、元の文と比べて、中身が抜けたり変わったりしていないかを確かめる。
    - アーティファクトのドキュメントや Markdown の文書では、直したい文を選び、「Edit with Claude」を押して依頼を書くと、Claude は選んだ場所だけを直す。どの節のことかを言葉で説明しなくてよい。
    - 選んで直す機能がなくても、チャットで「第 3 節だけを書き直して。ほかの節は変えないで」と頼めば、同じ考え方になる。
- **公式ドキュメント**
  - 「Reduce hallucinations」の「Iterative refinement」。出力を次の依頼に使って、確かめたり詳しくしたりする方法として紹介されている。
  - ヘルプセンター「What are artifacts and how do I use them?」の「Edit and iterate」（選んだ文だけを直す操作）。
- **試験での見分け方**
  - 「読み手」が問題文に書かれていたら、それに合わせて直す選択肢を選ぶ。読み手を考えずに「もっと詳しく」とだけ頼む選択肢は、弱い。
  - 「ほとんど承認済み」「1 か所だけ指摘された」とあれば、その部分だけを直す選択肢を選ぶ。全体を書き直す、作り直す選択肢が正解になるのは、文書全体が読み手に合っていないとき。
- **紛らわしいもの**
  - 読み手に合わせて言い回しを変えても、事実を変えてはいけない。簡単に言い換えるときに、内容が不正確にならないかを確かめる。
  - 難しい部分はそのままにして用語集を付けるのは、読み手に合わせたことにならない。読み解く手間を読み手に負わせている。

## 項目 6　情報を整理、選別し、出力の形式を選ぶ

- **要点**
  - 読み手に要る情報を選び、要らない情報を省く。
  - 出力の形式を、使い方に合わせて選ぶ。
  - 形式を選ぶことは、見せ方だけでなく、**結果をどこまで信頼できる必要があるか**の判断でもある。特に、数字が正しくなければならないときは、コード実行を選ぶ。

| 形式 | 向いているもの |
|---|---|
| インライン | 短い答え、その場で読めばよい説明、会話の続き |
| アーティファクト | まとまった長さがあり、それだけで読めて、あとで直したり、会話の外で使ったりするもの（文書、コード、図、小さなツールなど） |
| 構造化データ | ほかのツールに取り込むもの、項目をそろえて比べるもの（表、JSON、CSV など） |
| コード実行の結果 | 報告や判断に使う数字（合計、順位など）、グラフ、処理したファイル |

- **コード実行で数字を出す**
  - Claude に数字を「文章として書かせる」と、もっともらしいが、確かめられない数字が出る。答えのように見えても、推測にすぎない。
  - コード実行では、Claude がコードを書いて実際に計算する。計算の結果に加えて、グラフや処理したファイルも返る。数字が、どのデータから出たのかを、あとから確かめられる。
  - ただし、コード実行で**決まった結果になる**（同じデータと同じコードなら、何度動かしても同じ結果になる）のは、計算そのものだけ。コードを書くのは Claude なので、コードの考え方に誤りがある可能性は残る。言えるのは、コードを読んで確かめ、動かし直せるということ。コードが自動的に正しいということではない。
  - 文章で書かせた数字が、いつも悪いわけではない。大まかな感じをつかむだけなら、それで足りることもある。報告する数字には、コード実行を使う。
  - 誤った数字は、その数字を使うあとの資料（スライドなど）に、すべて広がる。
- **入力を整える**：整理された入力からは、整理された出力が返る。入力を整えるとは、必要な資料を加えるだけでなく、要らない資料を除くことでもある。次の 3 つで、たいていは足りる。
  1. 重複を除く。ほとんど同じ文書を何通も渡さない。
  2. 資料に**ラベル**（その資料が何かを示す見出しや説明）を付け、役割を分かるようにする。例：「これは承認済みの方針」「これらは下書き」。
     - ラベルがないと、Claude には、どれが正式な版で、どれが参考や古い下書きなのかが分からない。食い違う内容を、同じ重みで混ぜてしまう。
     - claude.ai で使うときは、XML を書かなくてよい。依頼文に「添付の『方針_承認済み.pdf』が正式な版で、ほかの 2 つは古い下書き」のように、ふつうの文で役割を書けば、それがラベルになる。資料を貼り付けるときは、「【承認済みの方針】」「【参考：よくある質問】」のような見出しで区切るだけでよい。大事なのは書き方ではなく、役割が分かること。
     - API でプロンプトを組み立てるときは、**XML タグ**（`<document>` のように、山かっこで囲んだ名前で、内容の始まりと終わりを示す目印）で資料を囲む書き方がよく使われる。公式のプロンプトの手引きは、資料を 1 つずつ `<document>` タグで囲み、出どころを `<source>`、本文を `<document_content>` のタグに入れる形を勧めている。
     - 例：`<document>` の中に `<source>承認済みの方針（2026 年 10 月版）</source>` と本文を入れ、別の `<document>` に `<source>よくある質問（参考）</source>` と本文を入れる。
     - 長い資料は、プロンプトの先頭に置き、質問はそのあと（最後）に書く。
  3. 質問に関係のない資料を除く。入力の雑音は、そのまま出力の雑音になる。
  - あわせて、ほしい出力の形（見出し、表の列など）をはっきり示す。そうすると、自分で並べ直す手間のない出力が返る。
  - 整理され、ラベルの付いた、必要最小限の入力のほうが、区別の付かない大量の資料よりも、すっきりした結果になる。

- **公式ドキュメント**：ヘルプセンターの「What are artifacts and how do I use them?」。Claude がアーティファクトを作るのは、内容が大きくてそれだけで完結している（おおむね 15 行より長い）、会話の外で直したり使い直したりしそう、会話の文脈がなくても分かる、あとで見返しそう、という場合とされている。
- **公式の教材**
  - 準備コース「出力の評価と検証」のレッスン 7「出力形式の選択：インライン、Artifacts、構造化、コード実行」。形式は、結果の使い道と、求められる信頼性で選ぶとしている。
  - Platform Docs の「Prompting best practices」の「Structure prompts with XML tags」と「Long context prompting」。資料を XML タグで囲み、出どころなどの情報を付ける形を示している。
- **試験での見分け方**
  - 「あとで直す」「人に渡す」「ほかのツールで使う」が問題文にあれば、インラインではない形式を考える。
  - 数字が報告や意思決定に使われるなら、コード実行を選ぶ。「計算」という言葉がなくても、ファイルの数字を集計する作業なら同じ。
  - 出力が散らかる、資料の取り違えがある、という問題では、入力を整える選択肢（重複を除く、ラベルを付ける、関係のない資料を除く）を考える。
- **紛らわしいもの**
  - アーティファクトにするかどうかは、長さだけでは決まらない。会話の外で直したり使い直したりするか、会話の文脈がなくても分かるか、あとで見返すかも条件になる。
  - 「コード実行を使ったので、確かめなくてよい」は誤り。コードの考え方に誤りがあるかもしれない。確かめられるようになるだけで、正しさが保証されるのではない。
  - 「資料は多く渡すほどよい」は誤り。関係のない資料や重複は、出力の雑音になる。
  - 入力が原因で出力が乱れているとき、上位のモデルに替える、新しい会話で同じ資料を貼り直す、要約を長くさせる、は原因に対処していない。入力を整える選択肢を選ぶ。
- **アーティファクトの新しい仕組み**：2026 年 9 月 16 日より前にチャットで作ったアーティファクトは「レガシー」と呼ばれ、そのまま使えるが、新しくは作れない。今のアーティファクトは、テンプレート（ドキュメント、スライドなど）から作ることもできる。テンプレートから作ったものは、自分で直接打ち込んで直すこともできる。使うには、設定の「Capabilities」で、コード実行とファイル作成（新しい画面では「Create and edit files」）をオンにする。試験ガイド（2026 年 7 月）は、この仕組みより前に作られている。
