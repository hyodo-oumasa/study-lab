# Associate 分野 4：ワークフロー統合とソリューション設計

[Associate – Foundations](./associate) の出題分野 4「ワークフロー統合とソリューション設計」（Workflow Integration and Solution Design）を、試験ガイドの項目ごとに見ます。比重は 16% で、2 番目に大きい分野です。

ワークフローは、仕事の流れ（だれが、どの順番で、何をするか）のことです。ソリューション設計は、課題を解決するための仕組みや進め方を考えることです。この分野は、「Claude を一回使う」ではなく、「仕事の流れの中に Claude を組み込む」ための判断を問います。

- **個人の使い方とワークフローの違い**：「私は Claude を使っている」は、個人の習慣。「私たちのワークフローは Claude を使っている」は、チームで回す、毎回同じ手順で進むプロセス。この分野が扱うのは後者。
- **価値は、どの手順を任せるかの判断から生まれる**：すべてを自動化することが目的ではない。手順ごとに、AI に任せるか、人が担うか、人と AI が一緒に行うかを決める（委任）。誤った手順を自動化すると、かえってうまくいかなくなる。
  - 準備コースの例（架空）：同じ契約書のレビューに Claude を入れた 2 つのチーム。一方は、作業を書き出したうえで、Claude には修正案を作らせ、最終判断は弁護士が行った。レビューの時間は半分になり、品質も保てた。もう一方は、リスクが低いとされた条項の承認まで、人の確認なしに Claude に任せた。承認した条項が、だれも気づかない義務を生み、チームはツールの利用をやめた。
  - 使ったツールは同じで、違いは任せた手順だけ。取り消しにくく、影響の大きい判断（承認、最終判断）は人に残す。分野 2 のトリアージの基準（重大性、取り消せるかどうか）と同じ考え方。

## この分野の項目

試験ガイドは、この分野について 5 つの項目を挙げています。日本語版の試験ガイド（Version 1.0）の言い方に合わせ、短くまとめました。

| 番号 | 項目 |
|---|---|
| 1 | 要件とユースケースの分析に Claude を使う |
| 2 | 調査、計画、プロセスの最適化に Claude を使う |
| 3 | ソリューションの設計、開発、反復的な改善の支援に Claude を使う |
| 4 | 既存のワークフローに Claude を統合し、ワークフローを強化または再設計する |
| 5 | Claude の価値と限界を、ステークホルダーに伝える |

この分野で使う言葉です。

| 日本語 | 英語 | 意味 |
|---|---|---|
| 要件 | requirements | 成果物や仕組みが満たすべき条件 |
| 統合 | synthesis | いくつもの情報源から、検討する点を集め、選択肢を整理し、良い点と悪い点の兼ね合い（トレードオフ）をまとめること |
| タスク定義 | task definition | あいまいな業務の望みを、何を、だれのために、どう作るかまで具体的にした作業の決めごと |
| ユースケース | use case | 「だれが、何のために使うか」という具体的な使い方 |
| ステークホルダー | stakeholder | その仕事に関わる人や、影響を受ける人（上司、顧客、チームなど） |
| 委任力 | Delegation | AI活用力の 4D の 1 つ。自分でする作業、AI と一緒にする作業、AI に任せる作業を決める力 |
| 反復的な改善 | iterative improvement | 試して、結果を見て、直して、また試すことを繰り返して良くすること |

## 項目 1　要件とユースケースの分析に Claude を使う

- **要点**
  - 作業を始める前に、**目標と、良い結果とは何か**をはっきりさせる。AI活用力では、これを「問題認識」と呼び、委任力の最初の要素としている。
  - Claude に要件を整理させるときは、いきなり答えを作らせず、**Claude に質問させて**目標を詰めていくやり方がある。
  - 仕事の多くは、整理されていない情報（長い文書、まとまらないメールのやり取り、口頭の依頼）から始まる。Claude は、これを、ほかの人がそのまま動ける、確かめられる要件に変えるのが得意。資料を渡して、**要約ではなく、構造化した分析**（要件を抜き出し、整理し、あいまいな点や足りない点を指摘する）を頼む。
  - **業務の望みをタスク定義に変える**：「もっと良いレポートがほしい」のままでは、作業を始められない。どんなレポートを、だれのために、どのくらいの頻度で、どのデータから、どの形式で作るかまで具体的にする。一つひとつが、作るときの基準になり、終わったかどうかを確かめられる要件になる。
  - **準備コースの例：提案依頼書（RFP）への対応**。RFP は、顧客が提案を募るために出す文書。40 ページの RFP と社内のメールから、要件の表を作る。
    - 頼み方：要件を 1 つずつ抜き出させ、要件ごとに、短いラベル、RFP の該当箇所、メールの中にもう答えがあるか、あいまいで確認が要るか、を表で出させる。
    - 結果：1 行が 1 つの要件で、RFP の箇所とつながり、答え済みか未対応かが分かり、あいまいな要件には顧客への確認事項として印が付く。チーム全体で使える。
    - 毎回の仕事なので、単発のチャットではなく**プロジェクト**で行う。過去に採用された提案書はナレッジ、抜き出す形式はプロジェクトの指示、書式を整える手順はスキルに置く。技術的な作り込みは要らない。指示とナレッジはプロジェクトの中に、スキルはアカウント全体に置かれる（[分野 5](./associate-5-configuration-knowledge)）。
  - **要件を確かめる**：抜き出しは最初の手順にすぎない。続けて、Claude に自分で抜き出した表を見直させる。あいまいな要件、2 通りに読める要件、RFP では間接的にしか触れていない要件を示唆するもの、を挙げさせる。
    - これで、文の従属節に埋もれた要件や、評価の基準から読み取れる**隠れた要件**が見つかる。見落とすと、案件を失うことにつながる。
    - 構造化した表と、確かめる手順を組み合わせると、どちらか一方だけよりずっと確かな土台になる。分野 2 の考え方を、要件を決める段階で使うもの。
- **公式の教材**
  - AI活用力「委任力 (Delegation) を詳しく見る」。委任力を「問題認識、プラットフォーム理解、タスク委任」の 3 つに分けている。「プロジェクト計画と委任力」では、明確な目標が持てるまで Claude に質問してもらう手順を示している。
  - 準備コース「ワークフロー統合とソリューション設計」の「Claudeによる要件とユースケースの分析」。タスク定義への変換、RFP の例、要件を確かめる手順。
- **試験での見分け方**
  - 「まず Claude に作らせる」より、「目標と条件を先にはっきりさせる」選択肢を選ぶ。
  - 整理されていない資料から要件を作る場面では、「要約させる」より、「要件を 1 つずつ抜き出し、出どころ、答え済みかどうか、あいまいさを表にさせる」選択肢を選ぶ。
  - 抜き出しで終わる選択肢より、あいまいな要件や隠れた要件を探す手順まで入れた選択肢を選ぶ。
- **紛らわしいもの**
  - 要件を整理するのは人と Claude の共同作業で、最後に要件を決めるのは人。Claude の整理をそのまま要件にしない。
  - Claude に自分の表を見直させるのは、あいまいな点や隠れた要件の**候補を洗い出す**ため。事実が正しいことの確かめにはならない（分野 2）。見つかったあいまいな点は、顧客に確認して決める。

## 項目 2　調査、計画、プロセスの最適化に Claude を使う

- **要点**
  - **調査**：いくつもの情報源を調べてまとめる調査には、リサーチ機能が向いている。リサーチ機能は、複雑な依頼を小さな単位に分けて調べ、確かめやすい引用を付けて答える。
  - **計画**：大きな仕事を作業に分け、作業ごとに「人が向いているか、AI が向いているか」を決める。
  - **プロセスの最適化**：今の仕事の流れのどこに時間がかかっているかを洗い出し、AI に任せられる部分を探す。
  - **計画には、性質の違う 2 つの作業が混ざっている**
    - **統合**：Claude が得意な作業。情報源をまとめ、選択肢とトレードオフを整理する。ただし、確かめていない主張が入り込みやすいので、分野 2 の確かめ方を使う。
    - **計算**：必ず確かめる作業。計画が数字に頼っているなら、データをアップロードし、**コード実行**で計算させる（分野 2 の項目 6）。
    - 最も強い計画は、Claude の統合とコード実行の分析を組み合わせ、計画を「作られた数字」ではなく「計算された数字」の上に立てる。推測した稼働率から作った人員計画は推測にすぎない。実際の勤務記録をコード実行で分析して作った人員計画が、本当の計画。
  - **最新の情報**：学習した範囲より新しい情報は、ちょっとした調べものならチャットのウェブ検索、深く調べるならリサーチ機能を使う。
  - **準備コースの例：次の四半期の人員計画**
    - 過去 4 四半期のチケット件数のデータをアップロードし、コード実行で、件数の伸び方と、担当者 1 人あたりの処理件数（スループット）を計算させる。
    - その数字をもとに、今の解決時間を保つのに要る人数を Claude に提案させる。**提案の前提条件も示させる**。
    - 提案の信頼性は、もとの数字の信頼性で決まる。数字が計算で出ているので、計画の一つひとつの根拠を説明できる。
  - **Claude を使う手順と、人が判断する手順**
    - Claude の効果が最も大きいのは、多くの検討点を比べて整理する統合の手順。
    - リスクをどこまで受け入れるか、社内の事情など、人の判断が要る手順は人が担う。
    - 人員計画の例では、4 四半期のデータを根拠のある提案に変えるのが Claude。予算や採用の凍結など、**Claude に見えない事情**をふまえて採用を決めるのは、計画を担当する人。
- **公式の教材**
  - Claude 101「深掘り調査のためのリサーチ機能」。複雑な依頼を分けて情報を集めること、引用で検証しやすいことが挙げられている。
  - AI活用力「プロジェクト計画と委任力」。プロジェクトを主要な作業に分け、作業ごとに人と AI の強みを考える手順。
  - 準備コース「ワークフロー統合とソリューション設計」の「リサーチ、計画、プロセス最適化」。統合と計算の分け方、人員計画の例、人に残す判断。
- **試験での見分け方**
  - 「すべてを AI に任せる」は正解になりにくい。AI活用力も、目標はすべてを自動化することではなく、作業ごとに最も効果的な人と AI の組み合わせを作ることだとしている。
  - 計画が数字に頼る場面では、「実データをコード実行で計算し、その数字から Claude に提案をまとめさせる」選択肢を選ぶ。
  - 最終判断の選択肢では、予算、方針、社内の事情など、Claude に渡していない事情が関わるかを見る。関わるなら、判断は人。
- **紛らわしいもの**
  - 調査の結果は、分野 2 で見たとおり、引用元を確かめてから使う。
  - 数字をコード実行で計算しても、提案がそのまま決定になるわけではない。数字が確かになるのは根拠の部分で、採用するかどうかは人が決める。

## 項目 3　ソリューションの設計、開発、反復的な改善の支援に Claude を使う

- **要点**
  - 仕事に Claude を使う方法を考えたら、**小さく試して、結果を確かめ、直して、また試す**。
  - Claude 101 が紹介する方法：答えが分かっている過去の仕事（5〜10 個の例や、自分で分析済みのデータ）で Claude を試し、自分の結果と比べる。うまくいかないところは、指示を足したり例を見せたりして直す。何度直してもうまくいかなければ、その作業は任せない、と判断する。
- **公式の教材**：Claude 101「より良い結果を得る」の「ワークフローに合わせたClaudeの評価」。データ分析の例では、前の四半期のデータで試し、見落としを指示で直し、登録日がないと推測してしまうという限界を書き留めている。
- **試験での見分け方**：「いきなり本番の仕事で使い始める」より、「答えの分かっている例で試してから広げる」選択肢を選ぶ。
- **紛らわしいもの**：試して確かめても、責任はなくならない。新しいデータで使うときも、結果が理にかなっているかを確かめるのは人。

## 項目 4　既存のワークフローに Claude を統合し、強化または再設計する

- **要点**
  - 仕事の形に合わせて、Claude との働き方を選ぶ。

| 働き方 | 向いている仕事 |
|---|---|
| ターンごとにやり取りする | 答えによって次の質問が変わる仕事、途中の判断に関わり続けたい仕事、すぐ終わる仕事 |
| 作業を任せる | いくつもの手順がある仕事、完成したファイルが要る仕事、いくつものツールにまたがる仕事、決まった時間に繰り返す仕事 |
| ソフトウェアを作る（Claude Code） | 開発者の仕事 |

  - 作業を任せても、手を離すわけではない。Claude が計画を見せ、途中で方向を直せる。メールの送信など大事な操作は、承認を待つように設定できる。
  - 社内のツール（Google Drive、Slack など）とつなぐには、コネクターを使う。
  - **強化**は今の流れの一部を Claude に任せること、**再設計**は Claude を前提に流れそのものを組み替えること。
- **公式の教材**：Claude 101「デスクトップでClaudeとどのように仕事をするか」。働き方の 3 つの形と、それぞれに向いている仕事が書かれている。新しい Claude の画面では、ターンごとのやり取りと作業を任せることの区別はなく、どの会話でも両方できる、とも書かれている。
- **試験での見分け方**：問題文の仕事が「その場で考えながら進める」のか、「決まった手順を最後までやってほしい」のかを見る。
- **紛らわしいもの**：資料やスライドを 1 つ作るだけなら、作業を任せる必要はない。会話の中でアーティファクトとして作れる（分野 2 の項目 6）。

## 項目 5　Claude の価値と限界を、ステークホルダーに伝える

- **要点**
  - **価値**を伝えるときは、試した結果をもとに話す。「何でもできる」ではなく、「この作業では、このくらい正確だった」と伝える。
  - **限界**も伝える。事実と違う内容を作ることがある、最新の情報を持っていないことがある、などの限界と、それにどう備えるか（人が確かめる手順）をあわせて伝える。
  - 成果物に AI をどう使ったかを、関係者に**正直に伝える**（透明性）。
- **公式の教材**
  - AI活用力「倫理的責任 (Diligence) を詳しく見る」。透明性における倫理的責任を、全ての関係者に対して作業における AI の役割を正直に伝えること、としている。
  - Claude 101「より良い結果を得る」のデータ分析の例。検証した方法を使うことで、当て推量ではなく検証された自信に基づいて作業できる、尋ねられれば AI の役割について透明性を保つ、としている。
- **試験での見分け方**：期待を大きくしすぎる伝え方も、AI を使ったことを隠す伝え方も、正解になりにくい。試した結果と、限界への備えをセットで伝える選択肢を選ぶ。
- **紛らわしいもの**：「限界があるので使わない」と伝えるのが正しいとは限らない。限界を知ったうえで、どの作業に使うかを決めるのがこの分野の考え方。

>

整理されていない資料は、要約ではなく、確かめられる要件の表に変えます。そのうえで、隠れた要件を探します。

- **A（誤り）**：要約では、要件ごとの出どころや、答え済みかどうかが分かりません。
- **B（正解）**：表で抜き出し、さらに見直す手順を入れると、隠れた要件やあいまいな点が見つかります。
- **C（誤り）**：あいまいな点は顧客に確かめ、要件は人が決めます。
- **D（誤り）**：メールには、すでに答えた内容や、決まったことが入っています。要件の表に要る資料です。
