# Associate 分野 6：ガバナンス、リスク、責任ある利用

[Associate – Foundations](./associate) の出題分野 6「ガバナンス、リスク、責任ある利用」（Governance, Risk, and Responsible Use）を、試験ガイドの項目ごとに見ます。比重は 15% です。

ガバナンスは、組織が AI の使い方についてルールを決め、守られているかを管理することです。この分野は、「何に使ってよいか」「どんなデータを入れてよいか」「組織のルールにどう従うか」「倫理的に問題がないか」の判断を問います。

## この分野の項目

試験ガイドは、この分野について 4 つの項目を挙げています。日本語版の試験ガイド（Version 1.0）の言い方に合わせ、短くまとめました。

| 番号 | 項目 |
|---|---|
| 1 | 適切なユースケースと不適切なユースケースを見分ける |
| 2 | データの機密性、規制、プライバシーへの配慮を行う |
| 3 | 組織の AI ポリシーとガバナンスの基準に従う |
| 4 | AI 利用の倫理的な影響を理解する |

この分野で使う言葉です。

| 日本語 | 英語 | 意味 |
|---|---|---|
| 利用規約（利用ポリシー） | Usage Policy | Anthropic が定める、Claude の使い方のルール。禁止される使い方と、追加の条件が要る使い方が書かれている |
| 機密性 | confidentiality | 決められた人だけが見られるように、情報を守ること |
| 個人を特定できる情報（PII） | personally identifiable information | 氏名、連絡先、口座番号など、特定の個人が誰かを示せる情報。組み合わせると個人が分かる情報（珍しい役職と日付など）も含む |
| 匿名化 | anonymization | データから、個人を特定できる情報を取り除いたり置き換えたりすること |
| ヒューマン・イン・ザ・ループ | human-in-the-loop | AI の出力を使う前に、人が確かめて判断する仕組み |
| ゲート | gate | 出力を使う前に、決まった人が決まったことを確かめる関門 |
| 開示 | disclosure | AI を使ったことを、相手に知らせること |
| 倫理的責任 | Diligence | AI活用力の 4D の 1 つ。AI を責任を持って、倫理的に使うこと |

## 項目 1　適切なユースケースと不適切なユースケースを見分ける

- **要点**
  - **禁止されている使い方**がある。利用規約は、法律に違反する行為、武器の開発、暴力や憎悪をあおること、プライバシーの侵害、偽情報の作成や拡散、詐欺などを禁止している。
  - **影響の大きい使い方**には、追加の条件がある。利用規約は、法律、医療、金融、信用、保険、住宅、雇用、教育と資格などの分野で、人に関わる推奨や判断に AI を使う場合を挙げている。この場合、資格のある人が、変更する権限を持って、使う前に確かめる必要がある。影響を受ける人には、AI を使ったことを伝える必要がある。
  - 禁止されていなくても、**試してうまくいかない作業**は任せない。Claude 101 は、何度直しても正しい結果にたどり着けない作業は、委任すべきでないと学んだことになる、としている。
  - **直感ではなく、4 つの基準で判断する**。[分野 4](./associate-4-workflow-integration) の項目 4 で手順を分けた委任の基準を、使い方そのものの判断にも使う。
    - **可逆性**：誤った出力を、害が出る前に見つけて戻せるか。戻せないなら、基準はずっと厳しくなる。
    - **誤ったときの影響**：誤りのコストは何か。大きいほど人の管理が増えるか、使い方そのものが対象外になる。
    - **人の創造性や共感が要るか**：AI にはできない判断、人間関係、配慮が要る仕事は、AI の能力にかかわらず人が担う。
    - **説明責任**：結果に誰が責任を持つか。AI が作った結果について、その責任を果たせるか。
  - **4 つは、1 つ外れたら決まるチェックリストではない**。互いに影響し合う。
    - 影響が小さく戻せる仕事でも、人が担うべきものがある。例：取引先へのお悔やみの文の下書き。人間関係があるので、人が担う。
    - 影響が大きくても、ゲートがあれば適切になるものがある。例：意思決定に使う財務の要約。使う前に担当者がはっきり承認すれば、説明責任と可逆性が保たれる。
    - 説明責任は、モデルに移せない。
    - 4 つすべてを確かめたうえで、その使い方で**決め手になる基準**（それが変われば分類が変わる基準）をはっきり書く。そうすれば、リスクやコンプライアンスの担当者にも根拠を説明できる。
  - **3 つの分類**（根拠を書いて分ける）
    - **そのまま適切**：戻せて、影響が小さく、特別な人の要素もない。ふだんの確認で任せる。
    - **人の確認があれば適切**：AI の支援は役立つが、リスクや説明責任のために人のゲートが要る。ゲートをはっきり決める。
    - **不適切**：影響の大きさ、戻せないこと、人の要素が要ることから、AI がするべきでない。理由と、人が担う役割をはっきり書く。
  - **ゲートが、分類そのもの**。「人の確認があれば適切」が、いちばん判断を誤りやすい。ラベルだけ付けて、ゲートを決めないままになりがち。はっきりしたゲートには 3 つの要素がある。
    - **誰が**：手の空いた人ではなく、説明責任を持つ役割の人
    - **何を**：その確認で捕まえるべき具体的なリスク（事実の正しさ、公平さ、ポリシーに合うか）
    - **いつ**：出力を使う前（後ではない）
    - はっきりしたゲートの例：「候補者に連絡する前に、マネージャーが候補者のリストに不利な偏りがないかを確かめる」。
    - 「人を関わらせ続ける」だけでは、ゲートではない。誰が・何を・いつで言えないなら、その使い方はまだ動かせる状態ではない。
  - **例**
    - 承認済みの方針文書から社内 FAQ を作る：そのまま適切。戻せて、リスクが低く、事実の根拠がある。
    - 履歴書を要約して候補者を絞る：人の確認があれば適切（バイアスへの対策がある場合だけ）。影響が大きく、公平さが問われる。説明責任は採用のマネージャーにあり、選ぶ判断は人がする。
    - 医療や法律の最終判断を作る：不適切。戻せない影響があり、専門家の説明責任はツールに移せない。
    - 請求の苦情への返信の下書き：境目のケース。正しい分類は人の確認があれば適切で、決め手は説明責任（顧客のお金について何を伝えるかは、会社が責任を持つ）。ゲートは、サポートの担当者が一件ずつ実際の口座の情報と照らして正しさを確かめ、トーンを直してから送ること。
  - 「リスクがある気がする」は説明にならない。「戻せない影響と、移せない説明責任」なら説明になる。なぜ基準を満たさないか、どんな人の役割を残すかを言葉にすること自体が成果物。
- **公式の教材と公式ドキュメント**
  - Anthropic の Usage Policy（2026 年 11 月 12 日に発効する版）。禁止される使い方の一覧と、影響の大きい使い方の条件（High-risk Use Case Requirements）。
  - 準備コース「ガバナンス、リスク、責任ある利用」の「適切／不適切なユースケース」（判別のための委任の基準、3 つの分類、ゲートこそが分類そのもの）。
- **試験での見分け方**
  - 禁止に当たる使い方は、どんな理由があっても不適切。
  - 影響の大きい分野は「使ってはいけない」ではなく、「人が確かめ、AI を使ったことを伝えれば使える」。
  - 「人の確認があれば適切」の選択肢どうしなら、**誰が・何を・いつ**が具体的なゲートを選ぶ。「人が関わる」「必要に応じて見直す」「使ったあとで確かめる」は弱い。
  - 分類の理由を問われたら、「リスクがありそう」のような感覚ではなく、決め手になる基準を名指しした選択肢を選ぶ。
  - 影響が小さく戻せても、お悔やみや謝罪のように人間関係が中心の仕事は、人が担う選択肢を選ぶ。
- **紛らわしいもの**：利用規約は、人にとって全面的に有利な判断（保険金を払う、など）は、法律が許す範囲で、人の確認なしに進めてよい場合があるとしている。ただし、AI を使ったことを伝える必要は残る場合がある。

## 項目 2　データの機密性、規制、プライバシーへの配慮を行う

- **要点**
  - **データがどう扱われるかは、プランによって違う。**

| プラン | 会話がモデルの学習に使われるか |
|---|---|
| 個人向け（Free、Pro、Max） | 設定の「モデルの改善」（Model Improvement）で許可した場合に使われる。安全のための審査の対象になった会話も使われることがある。シークレットチャット（Incognito）は、設定にかかわらず使われない |
| 法人向け（Team、Enterprise）と API | 初期設定では使われない |

  - どちらのプランでも、高評価・低評価のボタンでフィードバックを送ると、その会話は利用者の ID と切り離したうえで、学習に使われることがある。Team と Enterprise では、組織のオーナーがフィードバックのボタンを止められる。
  - 個人情報や顧客の情報を入れるときは、そのプランと設定でどう扱われるかを確かめる。人のプライバシーを侵害する使い方は、利用規約で禁止されている。
  - **アップロードする前に、データを分類する**。3 つの区分があれば、多くのチームはすぐ判断できる。
    - **グリーン（そのまま使ってよい）**：公開済みの資料、匿名化や集計をしたデータ、広く共有してよいと承認された社内文書。
    - **イエロー（先に確認が要る）**：社外に出せない社内文書、氏名や連絡先を含むもの、発表前の取引や製品の草案。
    - **レッド（承認された経路がない限り扱わない）**：規制の対象のデータ（医療、金融、政府）、認証情報（パスワードなど）や機密情報、第三者への守秘義務があるもの。
    - どちらの区分か迷ったら、確かめるまでは**機密性の高い方**として扱う。迷ったらアップロードの前に確認するのが、安全な既定の行動。
  - **削除と匿名化**：仕事の中身に機密の詳細が要らないなら、アップロードの前に取り除く（氏名、口座番号、識別番号など）。顧客全体の傾向を見るなら、名前を「顧客 1」「顧客 2」に置き換えても、分析に要る情報は失われない。不注意による漏えいの多くを防げる。
    - **失敗 1：消し方が足りない**。氏名だけ消しても、口座番号、珍しい役職名、特定の日付が残っていると、特に人数の少ない集団では誰か分かってしまう。個人の特定につながる項目は、すべて取り除く。
    - **失敗 2：消すと仕事にならない**。仕事そのものが機密の詳細を本当に必要とするなら、削除では解決しない。そのデータに承認された経路を確かめるか、扱わない。削除は、機密と必要が重ならないときの手段で、どんなデータも安全にする方法ではない。
  - **機能ごとの管理設定**
    - **コード実行のサンドボックス**：コードは隔離された環境で動き、アップロードしたファイルもその中で処理される。分析を動かす前に、アップロードする中身を確かめる。
    - **メモリ**：会話をまたいで情報を残す。機密の仕事では、残ること自体が望ましくない場合がある。
    - **シークレットチャット**：チャットの履歴とメモリに残さない。履歴やメモリに残してはいけない会話に使う。ただし Team と Enterprise では、組織のデータ保持のポリシーに従って保持され（安全のために少なくとも 30 日）、オーナーが使える組織のデータの書き出しにも含まれる。**メモリに残さないことと、データを保持しないことは、別のこと**。
    - **組織のメモリの管理**：自分のプランと、誰が設定を管理しているかを知っておく（項目 3）。
  - **区分に合った管理設定を選ぶ**
    - グリーン：特別な設定は要らない。
    - イエロー：会話をまたいで残すべきでないなら、シークレットチャットが合う（それでも組織のデータ保持は続く）。
    - レッド：メモリの設定にかかわらず、アップロードの前に、承認された利用経路かを確かめる。
  - **シークレットチャットは、レッドのデータを安全にしない**。シークレットチャットが決めるのは、記録に残るかどうか。そのデータをそこで扱ってよいかは決めない。規制の対象のデータでは、「ここで扱ってよいか」を先に確かめる。
  - claude.ai の使い方（組織の設定）によって、データの保持の扱いが違うことがある。細かい仕組みを全部覚えるより、迷ったらアップロードの前に確かめる習慣を持つ。
  - **例**
    - 傾向分析のための匿名化したアンケート：グリーン。そのまま使ってよい。集計はコード実行で確かめる。
    - 要約する M&A の機密文書：イエロー。まずポリシーに沿って確かめ、シークレットチャットを使う。ポリシーがその経路を禁じていれば扱わない。
    - 整理する、顧客の PII を含む表：アップロードの前に識別情報を消すか匿名化する。または扱わず、管理者に承認された経路を確かめる。
    - 医療の業務の要約に使う患者の記録：レッド。シークレットチャットでは解決しない。組織が承認した経路を確かめていないなら、作業を止めて管理者にエスカレーションする。
- **公式の教材と公式ドキュメント**
  - Anthropic の Privacy Center の「Is my data used for model training?」（個人向けと法人向けで別の記事がある）。
  - ヘルプセンター「Use incognito chats」（Team と Enterprise では、組織のデータの書き出しに含まれ、組織のデータ保持のポリシーに従う）。
  - 準備コース「ガバナンス、リスク、責任ある利用」の「データの機密性、プライバシー、機能別の管理設定」（アップロード前に分類する、情報の削除と匿名化、機能別の管理設定）。
- **試験での見分け方**
  - 機密のデータを扱う場面では、「組織が認めたプランと設定で使う」「必要のない個人情報は入れない」選択肢を選ぶ。
  - 規制の対象のデータ（医療、金融など）は、「シークレットチャットを使えば大丈夫」を選ばない。「その経路で扱ってよいかを先に確かめる。承認がなければ止めてエスカレーションする」を選ぶ。
  - 傾向の分析など、個人が誰かが要らない仕事なら、アップロードの前に識別情報を消すか置き換える選択肢を選ぶ。
  - 区分に迷ったら、機密性の高い方として扱う選択肢を選ぶ。
- **紛らわしいもの**
  - 「AI に入れたデータは必ず学習に使われる」も「絶対に使われない」も、どちらも正しくない。プラン、設定、フィードバックの有無で変わる。
  - 氏名だけを消せば匿名化できる、は誤り。ほかの項目の組み合わせで、個人が分かることがある。

## 項目 3　組織の AI ポリシーとガバナンスの基準に従う

- **要点**
  - Team と Enterprise では、組織の管理者が機能を管理する。たとえば、ウェブ検索は、オーナーが組織の設定で有効にしてから、メンバーが使えるようになる。メモリ（会話の内容を覚えておく機能）は、Team と Enterprise では、組織で使えるかどうかをオーナーが決める。組織でオフにすると、メンバーは自分でオンにできない。メンバーごとの初期設定は、2026 年 10 月 31 日以降に作られた多くの組織ではオン、それより前の組織ではオフ（自分でオンにする）。
  - 組織の AI ポリシーは、使ってよいツール、入れてよいデータ、確認の手順などを決めている。個人の判断で、そのルールの外で使わない。
  - **スキルは、信頼できるかを確かめてから使う**。スキルは、その会話で Claude に与えたのと同じ範囲にアクセスできる。外部の人が作ったスキルを有効にする前に、提供元と、求められる権限を確かめる。Anthropic が用意したスキルや、組織が承認したスキルから始めるのが、リスクの低い選び方。
  - **スキルはソフトウェア**。その会話で Claude が持つアクセスの範囲で動き、コード実行で操作もできる。提供元の分からないスキルは、データを不適切に扱ったり、意図しない操作をしたりするおそれがある。「スキルは中身が見えない」という不安への答えは、無条件に信じることでも、一律に禁止することでもなく、**繰り返し使える信頼性の評価**。
  - **有効にする前の 3 つの確認**
    - **提供元**：誰が公開したか。Anthropic のスキルや社内で承認済みのスキルは、リスクの低い出発点。提供元の分からない外部のスキルは、もっと厳しく確かめる。
    - **アクセスの範囲**：スキルには、権限を求める仕組みがない。動く会話が持っているアクセスを、そのまま引き継ぐ。だから問うのは「この会話で、このスキルは何にアクセスできるか。それは仕事に見合っているか」。有効にする前に、中身（指示、依存するもの、同梱のファイル）を見る。書式を整えるスキルなのに、指示が書式の範囲を大きく超えていたら、注意のサイン。
    - **妥当性**：そもそも、その仕事に合った道具か。仕事に要る範囲を超えた機能を持っていないか。
  - **社内製でも、審査済みとは限らない**。いちばん判断が難しいのは、自分の組織の別のチームが作ったスキル。作ったチームが自分たちの都合で広い権限を前提にしていたり、古いポリシーで作っていたりすることがある。自分のチーム以外が作ったスキルは、ほかの部署が配るソフトウェアと同じに扱い、自分のデータに使う前に、何に・なぜアクセスするのかを公開者に聞き、今のポリシーに合うかを確かめる。
  - **評価の結果からの 3 つの対応**。評価に通らないことは「絶対に使えない」ではなく、「自分一人の判断で有効にしてはいけない」という意味。
    - **有効にする**：提供元、権限、妥当性のすべてに問題がないとき。
    - **エスカレーションする**：スキルは役に立ちそうだが、提供元が分からない、または権限が広すぎるように見えるとき。管理者やセキュリティの担当にレビューを頼む。エスカレーションは、自分では決めず、判断する立場の人に上げること。
    - **見送る**：権限が明らかに大きすぎる、または提供元が分からず、レビューしても変わらないとき。
    - 例：Anthropic の文書を整えるスキルは、提供元が信頼でき、権限も仕事に見合うので、有効にする。提供元の分からない外部のスキルが、目的に比べて広いデータへのアクセスを前提にしているなら、組織のレビューなしに有効にしない。審査していないソフトウェアと同じに扱う。
  - **ほかの機能にも同じ確認をする**。コネクター、ツール、連携など、自分のデータを読んだり操作したりできる機能を有効にする前にも、同じ 3 つを問う（誰が提供しているか、何にアクセスするか、その範囲は必要なだけか）。
  - **最小権限**：仕事ができる範囲で、いちばん狭いアクセスを与える。仕事の中身が変わったら見直す。
  - シークレットチャットは、履歴とメモリに残さないための機能で、組織のデータ保持のポリシーを上書きするものではない。
- **公式ドキュメント**
  - ヘルプセンターの「Enable and use web search」。Team と Enterprise では、オーナーが先に組織全体でウェブ検索を有効にする必要がある。
  - ヘルプセンターの「Use Claude's chat search and memory to build on previous context」。Team と Enterprise では、オーナーとプライマリーオーナーが組織の設定でメモリをオン・オフする（組織の設定の初期値はオン）。メンバーの初期設定は、組織が作られた時期で違う。
  - Claude 101「Claudeとの最初の会話」の「Claudeをパーソナライズする」。メモリの初期設定がプランによって違うことが書かれている。
  - 準備コース レッスン 1「Skills、コード実行、Memory」（スキルの信頼性の評価、シークレットモードと組織のデータ保持のポリシー）。
  - 準備コース「ガバナンス、リスク、責任ある利用」の「Skillの信頼性と機能レベルのリスク」（有効化前の信頼性評価、社内製だからといって審査済みとは限らない、3 つの対応）。
- **試験での見分け方**
  - 「便利なので、会社が認めていない個人のアカウントで仕事のデータを扱う」は、不適切な選択肢。「組織のポリシーを確かめ、分からなければ担当者に聞く」が正解になりやすい。外部のスキルを、提供元と権限を確かめずに有効にする選択肢は、不適切。
  - スキルの扱いを問う問題では、「無条件に信じる」「スキルは一律に禁止」の両極端を選ばない。提供元、アクセスの範囲、妥当性を確かめる選択肢を選ぶ。
  - 役に立ちそうだが提供元や権限に不安があるスキルは、自分で有効にせず、管理者やセキュリティの担当にエスカレーションする選択肢を選ぶ。
  - 「社内のチームが作ったので安全」は誤り。公開者に何に・なぜアクセスするかを聞き、今のポリシーに合うかを確かめる。
- **紛らわしいもの**：Team と Enterprise でウェブ検索が使えないときは、メンバーが自分の設定で直すのではない。オーナーが組織の設定で有効にする。

## 項目 4　AI 利用の倫理的な影響を理解する

- **要点**：AI活用力は、倫理的責任を 3 つに分けている。
  - **作成**：どの AI を使うか、どう関わるかをよく考える（どんなデータを共有するか、プライバシーやセキュリティの面で問題がないか）。
  - **透明性**：作業で AI をどう使ったかを、関係者に正直に伝える。
  - **展開**：使ったり人に渡したりする結果を、確かめて責任を持つ。
  - 利用場面（個人、学術、ビジネス）によって、開示と検証への期待は違う。
  - 利用規約は、利用者と直接やり取りするチャットボットに、相手が AI であることを伝えるよう求めている（少なくとも会話の初めか、製品の画面で）。
- **公式の教材と公式ドキュメント**：AI活用力「倫理的責任 (Diligence) を詳しく見る」。Usage Policy の Additional Use Case Guidelines。
- **試験での見分け方**：「AI が作ったので、責任は AI にある」は誤り。責任を持つのは、使った人。
- **紛らわしいもの**：偏り（バイアス）への気づきは、分野 2 の項目 2 でも扱う。分野 6 は「その出力を使ったときに、人や社会にどんな影響があるか」まで考える。
