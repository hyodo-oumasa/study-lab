## 3.1 CLAUDE.md の階層

### 置き場所と、読み込まれる順番

CLAUDE.md は、次の 4 か所に置けます。上から順に、範囲が広いものから読み込まれます。

| 範囲 | 場所 | 共有される相手 |
|---|---|---|
| 組織（管理） | macOS では `/Library/Application Support/ClaudeCode/CLAUDE.md` など | 組織の全員 |
| 利用者 | `~/.claude/CLAUDE.md` | 自分（すべてのプロジェクト） |
| プロジェクト | `./CLAUDE.md` または `./.claude/CLAUDE.md` | チーム（Git で共有） |
| 自分だけ（プロジェクト） | `./CLAUDE.local.md` | 自分（そのプロジェクト） |

押さえておく点は、次のとおりです。

- **上書きではなく、つなげて読み込まれる。** 後から読まれたもの（作業フォルダーに近いもの）ほど、最後に読まれる。同じフォルダーでは、`CLAUDE.local.md` が `CLAUDE.md` の後に読まれる。
- **作業フォルダーより上のフォルダーの CLAUDE.md は、起動したときに読み込まれる。** 下のフォルダー（サブフォルダー）の CLAUDE.md は、Claude がそのフォルダーのファイルを読み書きしたときに、はじめて読み込まれる。
- **チームで共有したい決まりは、プロジェクトの CLAUDE.md に書く。** 利用者の CLAUDE.md に書くと、ほかのメンバーには届かない。
- **矛盾する指示があると、Claude はどちらかを選んでしまうことがある。** 定期的に見直す。

### どの CLAUDE.md が読み込まれているかを確かめる

| コマンド | 分かること |
|---|---|
| `/memory` | 利用者とプロジェクトの CLAUDE.md、`CLAUDE.local.md` などの置き場所の一覧。選ぶとエディターで開ける（まだないファイルは、作られる） |
| `/context` | 起動したときに、どの CLAUDE.md とルールが読み込まれたか |

たとえば、「新しく加わったメンバーにだけ、決まりが効かない」場合は、決まりがプロジェクトの CLAUDE.md ではなく、誰かの `~/.claude/CLAUDE.md`（その人だけに効く）に書かれていないかを疑います。

### インポート

CLAUDE.md の中に `@パス` と書くと、そのファイルが一緒に読み込まれます。

- 相対パスは、作業フォルダーではなく、**書いたファイルの場所から**たどる。
- 取り込んだファイルから、さらに取り込める。ただし、**4 段まで**。
- バッククォートで囲むと、取り込まずに文字のまま残る。

## 3.2 スラッシュコマンドとスキル

### コマンドとスキルは、同じ仕組みになった

`.claude/commands/deploy.md` と `.claude/skills/deploy/SKILL.md` は、どちらも `/deploy` を作り、同じように動きます。`.claude/commands/` は古い形で、今も使えます。新しく作るなら、補助のファイルを置けるスキルが勧められています。

| 置き場所 | 範囲 |
|---|---|
| `~/.claude/skills/` | 自分のすべてのプロジェクト |
| `.claude/skills/` | そのプロジェクト（Git で共有できる） |

同じ名前のスキルが両方にあると、**自分の（`~/.claude/skills/` の）スキルが優先**されます。チームのスキルを自分用に変えたいときは、別の名前を付けて自分の置き場所に作ると、チームのスキルも残り、ほかのメンバーにも影響しません。

**スキルと CLAUDE.md の使い分け：** いつも守ってほしい決まりは CLAUDE.md に、特定の作業の手順は、その作業のときだけ読み込まれるスキルに書きます。

### 試験で押さえるフロントマター

| 項目 | 働き | 使いどころ |
|---|---|---|
| `description` | 何をするスキルか、いつ使うか。Claude はこれを見て使うかを決める | 使ってほしい場面を、はじめに書く |
| `argument-hint` | 入力の補完のときに出る、引数の案内 | `[issue-number]` など |
| `allowed-tools` | そのスキルを使った回の応答の間、確認なしで使える道具 | 決まったコマンドだけを動かすスキル |
| `disable-model-invocation: true` | Claude が自分の判断では使わない。利用者が `/名前` で呼んだときだけ動く | デプロイなど、外部に影響する作業 |
| `user-invocable: false` | 利用者は呼び出せない。Claude だけが使う | 背景の知識 |
| `context: fork` | **会話の履歴を持たない別の Claude（サブエージェント）で動かす** | 大量に読み込む調査など、元の会話のコンテキストを汚したくない作業 |
| `agent` | `context: fork` のときに使うサブエージェントの種類 | 調査向けのサブエージェントを使う、など |

`context: fork` の注意点は、次のとおりです。

- 別の Claude は、それまでの会話を見られない。**スキルの指示だけで仕事が完結するように書く。**
- 名前に「fork」とあるが、会話を引き継ぐ「会話の分岐」とは別物。会話の内容が必要な作業には向かない。
- 既定では、裏で動き、終わると結果が会話に届く。`background: false` で、終わるまで待たせられる。`-p`（対話なしの実行）では、常に終わるまで待つ。

## 3.3 ファイルの場所ごとのルール

`.claude/rules/` に置いた Markdown のファイルは、ルールとして読み込まれます。フロントマターに `paths` を書くと、**当てはまるファイルを扱うときだけ**読み込まれます。

```markdown
---
paths:
  - "src/api/**/*.ts"
---

# API を書くときの決まり

- すべての API で、入力を検証する
```

| 書き方 | 読み込まれるとき |
|---|---|
| `paths` なし | いつも（起動したとき） |
| `paths` あり | Claude が、当てはまるファイルを Read、Write、Edit で扱ったとき（`cat` などで 1 つのファイルを見たときも含む） |

- `paths` のパターンは、`.claude` フォルダーがあるフォルダーからの相対で書く。
- `{ts,tsx}` のように、波かっこで複数の拡張子をまとめられる。
- ルールのフロントマターで読まれる項目は、`paths` だけ。

**サブフォルダーの CLAUDE.md との使い分け：** サブフォルダーの CLAUDE.md は、そのフォルダーの中のファイルを扱うときに読み込まれます。テストのファイルのように、決まりを当てはめたいファイルが**あちこちのフォルダーに散らばっている**ときは、フォルダーごとに CLAUDE.md を置くより、`**/*.test.ts` のような `paths` のルールを 1 つ置くほうが向いています。

**CLAUDE.md とルールの使い分け：** どの作業にも必要な決まりは CLAUDE.md に、特定の種類のファイルにだけ必要な決まり（テストの書き方、API の書き方など）は `paths` 付きのルールに書きます。必要なときだけ読み込まれるので、コンテキストの節約になります。

## 3.4 Plan モードと、直接の実行の使い分け

公式のベストプラクティスは、作業の進め方を「調べる → 計画する → 実装する → コミットする」の 4 段階に分け、調べることと計画することを Plan モードで行うよう勧めています。ただし、Plan モードには手間もかかるので、使い分けが大切です。

| 使い分け | 作業の例 |
|---|---|
| **Plan モードを使う** | やり方に迷いがある。複数のファイルを変える。よく知らないコードを変える |
| **直接実行する** | 範囲がはっきりしていて、小さい変更。誤字の修正、ログの 1 行の追加、変数の名前の変更 |

公式ドキュメントの目安は、「**変更の中身を 1 文で説明できるなら、計画はいらない**」です。

2 つは組み合わせて使えます。たとえば、ライブラリーの入れ替えのような大きな作業は、Plan モードで調べて計画を立て、計画を承認したら、通常のモードで計画どおりに実装します。

### 調査用のサブエージェント（Explore）

Claude Code には、コードを調べるための組み込みのサブエージェント「Explore」があります。Claude は、変更をせずにコードを検索したり理解したりする必要があるときに、Explore に任せます。調べた過程の長い出力は Explore の側にとどまり、元の会話には要約だけが返るので、元の会話のコンテキストがいっぱいになりにくくなります。Explore は、起動を軽くするために、CLAUDE.md を読み込まずに始まります。

## 3.5 少しずつ良くしていく進め方

公式のベストプラクティスから、試験に関わる進め方を整理します。

| 進め方 | 内容 |
|---|---|
| **確かめる手段を渡す** | テスト、ビルド、期待する入力と出力の例など、Claude が自分で合否を確かめられるものを渡す。Claude は、確かめて、直して、を繰り返せる |
| **入力と出力の例を示す** | 「メールアドレスを検証する関数」ではなく、「`user@example.com` は正しい、`user@.com` は誤り」のように例を渡す |
| **症状ではなく、原因を直させる** | エラーの内容を渡し、エラーを隠さずに原因を直すよう頼む |
| **聞き取りのやり方** | 大きな機能では、まず Claude に質問させて、仕様を固め、仕様書に書かせる。実装は、新しい会話で仕様書をもとに行う |
| **関係する問題はまとめ、独立した問題は分ける** | 直し方が互いに影響する複数の問題は、1 通の詳しいメッセージにまとめて伝える。互いに関係しない問題は、1 つずつ直して確かめる |
| **早めに軌道を直す** | ずれたら `Esc` で止める。`/rewind` で前の状態に戻す。同じことを 2 回以上直しても直らないときは、`/clear` で会話を始め直し、学んだことを含めた具体的な指示を出す |

## 3.6 CI/CD への組み込み

### 対話なしで動かす（`-p`）

`claude -p "指示"` で、人が入力しなくても Claude Code が動きます。CI、Git のコミット前の点検、スクリプトなどに組み込む方法です。

| オプション | 働き |
|---|---|
| `-p` | 対話なしで、1 回の指示を実行する |
| `--output-format json` | 結果を JSON で返す。答えは `result` に入る。費用の見積もり（`total_cost_usd`）なども入る |
| `--output-format stream-json` | 結果を 1 行 1 つの JSON で、少しずつ返す（`--verbose` と一緒に使う） |
| `--json-schema` | `--output-format json` と一緒に使い、答えの形を JSON スキーマで決める。決めた形の答えは `structured_output` に入る |
| `--bare` | フック、スキル、MCP サーバー、CLAUDE.md などの自動の読み込みを省いて、速く起動する。CI ではこちらが勧められている |
| `--allowedTools` | 確認なしで使ってよい道具を指定する |

CI で使うときの注意点は、次のとおりです。

- **`structured_output` がないこともある。** Claude が依頼を断った場合などは、`structured_output` が入らない。スクリプトで使う前に、項目があるかを確かめる。
- **`-p` では、フォルダーの信頼の確認が出ない。** `--bare` を付けないと、プロジェクトの `.claude/settings.json` のフックや、`.mcp.json` の MCP サーバーが、確認なしで動く。知らないリポジトリで動かすときは、特に気をつける。
- **`--bare` を付けると、CLAUDE.md も読み込まれない。** CI の Claude に、テストの決まりや見直しの基準を伝える手段は、ふつうは CLAUDE.md です。`--bare` を付ける場合は、必要な決まりを `--append-system-prompt` などで明示的に渡します。

### CI での見直しと、テストの作成のコツ

| コツ | 理由 |
|---|---|
| **コードを書いた会話とは別の会話（別の Claude）に見直させる** | 書いた本人の会話は、書いたときの考え方に引きずられる。書いた過程を見ていない見直し役のほうが、問題に気づきやすい。ターミナル版の `/code-review` も、会話を見ていない別のサブエージェントで差分を見直す |
| **2 回目の見直しでは、前回の指摘を渡す** | 新しいコミットのあとに見直し直すとき、前回の指摘を渡して「新しい問題と、まだ直っていない問題だけ」を挙げさせると、同じ指摘のコメントが重ならない |
| **テストを作らせるときは、今あるテストを渡す** | すでにある場面のテストを、重ねて提案させないため |
| **テストの決まり、役立つテストの基準、使えるテスト用のデータを CLAUDE.md に書く** | 作られるテストの質が上がり、価値の低いテストが減る |

GitHub Actions の中で Claude を動かす方法は、「Claude Code」のテーマの 13（Claude Code を CI で動かす）で扱う予定です。

## 実際にやってみる

これまでのページで説明だけしていた 3 つのことを、このサイトのリポジトリで試しました。どれも、ターミナル版の `claude -p`（対話なしの実行）を使い、1 回ごとに新しい会話で確かめています。試し用のルールとスキルは、確かめたあとに消しました。

### 1. ファイルの場所ごとのルール

`.claude/rules/` に、次のルールを置きました。CI/CD のテーマのページ（`docs/cicd/` の下）を扱うときだけ読み込まれ、読み込まれたら答えの最後に目印を書くように指示したものです。

```markdown
---
paths:
  - "docs/cicd/**/*.md"
---

- このルールが読み込まれているときは、答えのいちばん最後の行に、「[RULE-CICD]」とだけ書く。
```

| 試したこと | 期待したこと | 結果 |
|---|---|---|
| `docs/cicd/index.md` を読ませて、要約させる（当てはまる） | 目印が付く | **付いた** |
| `README.md` を読ませて、要約させる（当てはまらない） | 目印が付かない | **付かなかった** |

### 2. `context: fork` のスキル

`context: fork` と `disable-model-invocation: true` を付けたスキルを作りました。スキルの中では、「この依頼より前の会話で、利用者が伝えた合言葉を知っていれば書く」ことと、「Claude Code のテーマのトップページを読んで、公開済みのページを数える」ことを頼んでいます。

会話の中で先に合言葉を伝えてから、このスキルを呼び出しました。

| 確かめたこと | 期待したこと | 結果 |
|---|---|---|
| スキルを動かした別の Claude は、合言葉を知っているか | 知らない（会話の履歴を見られない） | **「知らない」と答えた** |
| 別の Claude は、ファイルを読んで作業できるか | できる | できた（公開済みのページを 11 と数えた） |
| 元の会話の Claude は、合言葉を知っているか | 知っている | 知っていた |

別の Claude には会話の内容が渡らず、スキルの指示とファイルから分かることだけで作業する、ということを確かめられました。

### 3. `--json-schema` で答えの形を決める

公開済みのページの番号と数を、決めた形で答えさせました。

```bash
claude -p "docs/claude-code/index.md を読み、状態が「公開済み」のページの番号と、その数を答えてください。" \
  --allowedTools "Read" \
  --output-format json \
  --json-schema '{"type":"object","properties":{"published_count":{"type":"integer"},"page_numbers":{"type":"array","items":{"type":"string"}}},"required":["published_count","page_numbers"]}'
```

返ってきた JSON の `structured_output` は、次のとおりでした。

```json
{"published_count": 11, "page_numbers": ["01", "02", "03", "04", "05", "06", "07", "08", "09", "10", "11"]}
```

決めた形（数は整数、番号は文字の並び）で返ってきました。返ってきた JSON には、答えのほかに、セッションの ID、かかった時間、費用の見積もりなど、30 以上の項目が入っていました。

## まとめ

- CLAUDE.md は、組織、利用者、プロジェクト、自分だけ、の 4 か所に置ける。上書きではなく、つなげて読み込まれ、作業フォルダーに近いものほど後に読まれる。インポートは、書いたファイルの場所からたどり、4 段まで。
- スラッシュコマンドとスキルは同じ仕組み。`disable-model-invocation`、`user-invocable`、`allowed-tools`、`context: fork` の働きを区別する。`context: fork` のスキルは、会話の履歴を見られない。
- `paths` 付きのルールは、当てはまるファイルを扱うときだけ読み込まれる。特定の種類のファイルの決まりに使う。
- 変更を 1 文で説明できる小さな作業は直接実行し、迷いがある作業や大きな作業は Plan モードで計画する。
- Claude が自分で合否を確かめられるもの（テスト、例）を渡し、早めに軌道を直す。
- CI では `claude -p` を使う。`--json-schema` の答えは `structured_output` に入るが、入らないこともある。CI の Claude にも、決まりは CLAUDE.md で伝える（`--bare` を付けると CLAUDE.md は読み込まれない）。見直しは、コードを書いた会話とは別の会話に任せる。
