# Dependabot を導入して脆弱性を直すまで

このページは、このサイト（study-lab）に Dependabot を導入し、見つかった脆弱性 4 件を修正するまでの記録です。作業は AI エージェントの Claude Code と一緒に進めました。

前半では Dependabot の仕組みと、自動では直せなかった脆弱性をどう直したかを解説します。後半では、AI と作業を進める中で起きた認識のずれと、その対処をまとめます。

## 用語の整理

このページで使う主な用語です。

| 用語 | 意味 |
|---|---|
| 依存パッケージ | 自分のプロジェクトが使っている、ほかの人が作った部品（ライブラリやツール） |
| 脆弱性 | ソフトウェアのセキュリティ上の欠陥 |
| PR（プルリクエスト） | 「このファイルをこう変更したい」という提案を GitHub 上に出す仕組み。承認されるまで本番には反映されない |
| マージ | PR で提案された変更を、`main` ブランチ（本番のコード）に取り込むこと |
| ビルド | Markdown などのソースから、公開用の HTML を生成する作業 |
| CI（Continuous Integration） | 変更のたびに、自動でビルドやテストを行って確認する仕組み |
| デプロイ | ビルドした結果を公開すること |

## Dependabot とは

Dependabot は、GitHub に組み込まれている機能です。依存パッケージを定期的に調べて、更新や脆弱性への対応を手伝ってくれます。無料で使えます。

Dependabot には、役割の違う 3 つの機能があります。

| 機能 | 何をするか | 有効にする方法 |
|---|---|---|
| Dependabot alerts | 依存パッケージに脆弱性が見つかったら、アラート（警告の通知）を出す | リポジトリの設定 |
| Dependabot security updates | 脆弱性を直したバージョンへ更新する PR を、自動で作る | リポジトリの設定 |
| Dependabot version updates | 脆弱性がなくても、新しいバージョンが出たら更新の PR を定期的に作る | `.github/dependabot.yml` を置く |

## 設定のしかた

### 1. version updates の設定ファイル

リポジトリに `.github/dependabot.yml` を置きます。このサイトでは、npm パッケージと GitHub Actions のアクションを、毎週月曜の 9 時（日本時間）に確認する設定にしました。

```yaml
version: 2
updates:
  # npm パッケージ（package.json / package-lock.json）
  - package-ecosystem: "npm"
    directory: "/"
    schedule:
      interval: "weekly"
      day: "monday"
      time: "09:00"
      timezone: "Asia/Tokyo"

  # GitHub Actions のアクション（.github/workflows/*.yml の uses:）
  - package-ecosystem: "github-actions"
    directory: "/"
    schedule:
      interval: "weekly"
      day: "monday"
      time: "09:00"
      timezone: "Asia/Tokyo"
    # アクションの更新は 1 つの PR にまとめて届くようにする
    groups:
      github-actions:
        patterns:
          - "*"
```

- `package-ecosystem`：何の部品を見張るかを指定します。npm は `package.json` の部品、`github-actions` はワークフロー内の `uses:` で指定したアクションです。
- `groups`：複数の更新を 1 つの PR にまとめる設定です。アクションが 5 つあると、まとめないと PR が 5 つ届いてしまいます。

### 2. alerts と security updates の有効化

リポジトリの Settings にあるセキュリティ関連の設定画面で、Dependabot alerts と Dependabot security updates を有効にします。

GitHub CLI（コマンドで GitHub を操作するツール `gh`）を使う場合は、次のコマンドで有効にできます。

```bash
gh api -X PUT repos/OWNER/REPO/vulnerability-alerts
```

```bash
gh api -X PUT repos/OWNER/REPO/automated-security-fixes
```

`OWNER/REPO` の部分は、自分のリポジトリ名に置き換えてください（例：`hyodo-oumasa/study-lab`）。

## 導入後に起きたこと

設定を push すると、Dependabot はすぐに最初の確認を始めました。数分のうちに、次のことが起きました。

1. **アクションの更新 PR が届いた**
   5 つのアクション（`actions/checkout` など）を新しいバージョンに上げる PR が 1 つ届きました。これで、デプロイのたびに出ていた「Node.js 20 は非推奨」という警告が解消されます。

2. **PR にチェックが付かなかった**
   このときのワークフローは、`main` への push でしか動かない設定でした。そのため、PR の段階では「新しいアクションでもビルドできるか」を確かめる手段がありませんでした。そこで、PR のたびにビルドだけを試すワークフロー（`pr-build.yml`）を追加しました。そのうえで、PR に `@dependabot recreate` とコメントして PR を作り直してもらい、チェックを走らせました。

3. **脆弱性のアラートが 4 件出た**
   サイトを作る道具 VitePress が内部で使っている vite（開発サーバーを動かすツール）に 3 件、esbuild（プログラムを高速に変換するツール）に 1 件の脆弱性が見つかりました。どれも、手元で開発サーバーを動かしている間に、ほかの Web サイトから PC 内のファイルを読み取られるおそれがある、という種類のものでした。公開中のサイト（ただの HTML）には影響しません。

4. **自動修正はできず、Actions に「失敗」が記録された**
   security updates が修正の PR を作ろうとしましたが、作れませんでした。その記録が、GitHub の Actions 画面に「Dependabot Updates」という名前の失敗として残りました。サイトが壊れたわけではありません。**脆弱性を自動では直せなかった**、という意味です。

## 自動修正できなかった理由

失敗した記録のログには、`security_update_not_possible`（セキュリティ更新は不可能）というエラーと、その理由が書かれていました。

```text
"dependency-name": "vite",
"latest-resolvable-version": "5.4.21",
"lowest-non-vulnerable-version": "6.4.3",
"explanation": "vitepress@1.6.4 requires vite@^5.4.14"
```

| 項目 | 値 | 意味 |
|---|---|---|
| `lowest-non-vulnerable-version` | 6.4.3 | 脆弱性が直っている、いちばん低いバージョン |
| `latest-resolvable-version` | 5.4.21 | 今の構成で上げられる上限 |
| `explanation` | `vitepress@1.6.4 requires vite@^5.4.14` | VitePress が vite のバージョンを制限している |

### 制限をかけていたのは誰か

この制限は、**VitePress の開発チーム**がかけたものです。VitePress 自身の `package.json` に、次のように書かれています。

```json
"vite": "^5.4.14"
```

先頭の `^`（キャレット）は npm の記号で、「左端の数字（メジャーバージョン）は変えない範囲で、新しいものを使ってよい」という意味です。つまり「vite は 5.4.14 以上、6 未満」という指定になります。

::: info 0 から始まるバージョンの場合
esbuild のように `0.21.3` のような 0 始まりのバージョンでは、`^0.21.3` は「0.21.3 以上、0.22 未満」という、より狭い範囲を意味します。esbuild は vite を経由してこの範囲に制限されていました。
:::

メジャーバージョンが変わるときは、以前と互換性のない変更が入ることがあります。VitePress 1.6.4 の開発チームは vite 5 での動作しか保証していないため、このように制限していると考えられます。

### Dependabot が制限を超えない理由

Dependabot は、親の部品（ここでは VitePress）が指定した範囲の中でしかバージョンを上げません。親を新しい版に上げることで解決できないかも探しますが、新しい vite に対応した VitePress の安定版は、まだ出ていませんでした（2.0 は試験版のみ）。

親の指定を上書きするには、「保証のない組み合わせを使ってよいか」という人の判断が必要です。そのため、Dependabot はそこから先には進みません。これは故障ではなく、Dependabot の設計どおりの動作です。

## 人が選ぶ対応策

自動修正できない脆弱性には、人が対応策を選びます。

| 対応策 | 内容 | リスク |
|---|---|---|
| 親の更新を待つ | VitePress の新しい安定版を待つ | 待つ間、脆弱性が残る |
| 親を新しい版に上げる | VitePress 2.0（試験版）に移行する | 試験版のため、動作が不安定になるおそれがある |
| overrides で強制する | 内部の部品のバージョンを、こちらから指定する | 親の開発チームが保証していない組み合わせになる |
| ツールを変える | 別のサイト生成ツールに乗り換える | 作業量が大きい |
| リスクを受け入れる | 理由を記録して、アラートを閉じる | 脆弱性が残る。影響が小さいと判断できる場合に限る |

このサイトでは、**overrides で強制する**方法を選びました。変更が小さく、問題があればすぐに戻せるためです。

## 修正のしかた（overrides）

npm の `overrides` は、依存パッケージの内部で使われている部品のバージョンを、自分のプロジェクトの `package.json` から強制的に指定する機能です。

`package.json` に次の 3 行を追加しました。

```json
"overrides": {
  "vite": "^6.4.3"
}
```

追加したら、`npm install` を実行して `package-lock.json`（実際にインストールするバージョンの記録）を更新します。vite を上げると、vite の内部で使われている esbuild も一緒に新しくなります。

| 部品 | 変更前 | 変更後 |
|---|---|---|
| vite | 5.4.21 | 6.4.4 |
| esbuild | 0.21.5 | 0.25.12 |

### 確認したこと

保証のない組み合わせになるので、反映する前に次のことを確認しました。

| 確認 | コマンド | 結果 |
|---|---|---|
| 脆弱性が残っていないか | `npm audit` | 0 件 |
| サイトをビルドできるか | `npm run docs:build` | 成功 |
| 開発サーバーが動くか | `npm run docs:dev` | 各ページが表示された |
| 公開されるページの内容が変わらないか | ビルド結果の文章を比較 | 変化なし |

この変更は PR として出し、PR のビルドチェックに合格したことを確認してからマージしました。マージ後、Dependabot のアラート 4 件は自動で「解決済み（fixed）」になりました。

### 上書きを外す時期

`overrides` は一時的な対処です。VitePress が新しい vite に正式に対応した版を出したら、`overrides` を削除し、VitePress を上げる正規の方法に戻します。version updates が毎週確認しているので、新しい VitePress が出れば更新の PR が届きます。

## AI と進める中で起きた認識のずれと、その対処

この作業は Claude Code と一緒に進めましたが、AI の説明と、こちらの理解の間にずれが生じ、解決までに時間がかかりました。起きたずれと、その対処をまとめます。

| 起きたずれ | 影響 | 対処 |
|---|---|---|
| AI が「自動では直せない」を「直せない」と受け取り、脆弱性を残す方向で話を進めた | 解決が遅れた | 「見つけて、直すまで」を目的に置き直し、直し方を調べ直させた。その結果、overrides で直せると分かった |
| AI が「失敗」の意味（脆弱性を自動では直せなかったこと）を説明しないまま、失敗の表示を止める案（security updates の無効化）を勧め、同意を求めた。実質的には、脆弱性の放置につながる案への同意を求めていた | 判断に必要な情報がないまま、脆弱性を放置するかどうかを決めさせられそうになった | 「失敗」と言われたら、何が失敗したのか、それによって何が残るのかを AI に説明させる。表示や通知を止める案が出たら、止めた結果、何を見逃すことになるのかを確認する |
| AI が用語を説明せずに承認を求めた | 理解が追いつかないまま承認が進んだ | 承認の前に、何をするのか・何が起きるのか・リスクは何か・どう戻すのか、の 4 点を AI に説明させる |
| 想定内の結果を、AI が未知の問題のように報告した。同じ結果を「失敗」とも「成功」とも言った | 混乱して、確認のやり取りが増えた | 想定される結果は事前に伝えさせる。評価は「何を目的にして、何を期待していたか」を基準に述べさせる |

### AI に説明を求めるときのルール

上の対処をまとめたものです。AI エージェントへの指示文として、そのまま使える形にしています。

```text
- 用語や略語は、初めて出てくるところで意味を説明してください。
- 承認を求める前に、次の 4 点を示してください。
  1. 何をするのか
  2. その結果、何が起きるのか（想定される副作用も含めて）
  3. リスクは何か
  4. 問題があったとき、どう戻すのか
- 結論だけを先に言わず、何をしようとして、何が起きたのかを順に説明してください。
- 想定できる結果は、実行する前に伝えてください。結果を報告するときは、想定内か想定外かを最初に区別してください。
- 「成功」「失敗」と評価するときは、目的と期待していた結果を示してから述べてください。こちらの言葉に合わせて評価を変えないでください。
- ツールが「自動では直せない」と言っても、それを「直せない」と同じ意味に扱わず、ほかの解決策を調べてください。
- リスクを受け入れるかどうかは、あなたが決めずに、選択肢と根拠を示してこちらに判断させてください。
- 通知や表示を止める案を出すときは、止めた結果、何を見逃すことになるのかを説明してください。
```

## まとめ

- Dependabot には、脆弱性を知らせる alerts、自動で直す security updates、定期的に更新を提案する version updates の 3 つの機能がある。
- 間接的に使っている部品が、親の部品のバージョン指定（`^`）で古い範囲に縛られている場合、Dependabot は自動では直せない。Actions に記録される「失敗」は、そのことを意味する。
- 自動で直せない脆弱性は、人が対応策を選んで直す。overrides は有効な手段だが、保証のない組み合わせになるので、確認と、上書きを外す計画をセットにする。
- PR 用のビルドチェックは、Dependabot より先に用意しておくとよい。更新の PR が届いた時点で、自動で確認できる。
- 関連する PR をマージする順番に注意する。このサイトでは、アクションの更新 PR を脆弱性の修正 PR より先にマージしたため、その間に Dependabot の失敗の記録が 2 件増えた。
- AI と作業するときは、理解できるまで説明を求める。承認は、内容を理解してから行う。
