# 権限モードと、確認を減らす方法

Claude Code は、ファイルを書き換えたり、コマンドを実行したりする前に、「実行してよいか」を確認することがあります。この確認は、意図しない操作を防ぐための仕組みです。一方で、確認が多すぎると、作業が進みません。このページでは、確認が出る仕組みを整理し、安全さを保ったまま確認を減らす方法をまとめます。

## この記事で分かること

- どの操作で確認が出て、どの操作では出ないのか
- 6 つの権限モードの違いと、切り替え方
- 権限ルール（allow、ask、deny）の働きと、書き方
- 確認が多く出るときの、原因の見分け方と減らし方
- どの設定にしても確認が残る操作

## 用語の整理

| 用語 | 意味 |
|---|---|
| 権限の確認（permission prompt） | Claude が操作を実行する前に、利用者に「実行してよいか」を尋ねる表示 |
| 権限モード（permission mode） | 確認なしで実行できる操作の範囲を、セッション全体について決める設定 |
| 権限ルール（permission rule） | 特定のツールやコマンドについて、許可する、確認する、禁止する、を個別に決める設定 |
| allow / ask / deny | 権限ルールの 3 つの種類。allow は確認なしで許可、ask は毎回確認、deny は禁止 |
| 作業フォルダー（working directory） | Claude が、確認なしでファイルを読める範囲。既定では、セッションを始めたフォルダー |
| 分類器（classifier） | auto モードで、利用者の代わりに操作を審査する、別のモデル |
| 保護されたパス（protected path） | `.git` や `.claude` など、書き込みが自動では許可されないフォルダーやファイル |
| 管理設定（managed settings） | 組織の管理者が配布する設定。利用者やプロジェクトの設定では、上書きできない |

## 確認が出る仕組み

確認が出るかどうかは、次の 3 つで決まります。

1. **操作の種類**：読むだけの操作か、書き換えや実行を伴う操作か
2. **権限モード**：セッション全体で、どこまでを確認なしにするか
3. **権限ルール**：特定のツールやコマンドについての、個別の許可や禁止

まず、操作の種類ごとの基本の動きです。次の表は、Manual（すべての操作を自分で確認するモード）での動きです。

| 操作の種類 | 例 | 確認が出るか |
|---|---|---|
| 読み取り | ファイルを読む、検索する | 出ない（作業フォルダーの中の場合） |
| シェルのコマンド | `npm run build`、`git commit` | 出る。ただし、読み取り専用のコマンドは出ない |
| ファイルの変更 | ファイルの編集、作成 | 出る |
| Web ページの取得 | 指定した URL の内容を読む | 出る。ただし、あらかじめ許可されているドキュメントのサイトは出ない |
| Web 検索 | 検索する | 出る |

### 読み取り専用のコマンド

Claude Code は、あらかじめ決められた一部のコマンドを「読み取り専用」と見なし、どのモードでも確認なしで実行します。公式ドキュメントが挙げているのは、`ls`、`cat`、`echo`、`pwd`、`head`、`tail`、`grep`、`find`、`wc`、`which`、`diff`、`stat`、`du`、`cd` と、`git` の読み取りだけの使い方です。この一覧は、設定で変えられません。

ただし、これらのコマンドでも、確認が出る場合があります。たとえば、`ls > out.txt` のように結果をファイルへ書き出すと、書き出し先についての確認が加わります。

## 権限モード

権限モードは、セッション全体について、確認なしで実行できる範囲を決めます。

| モード（設定での値） | 画面での名前 | 確認なしで実行されるもの | 向いている場面 |
|---|---|---|---|
| `default` | Manual | 読み取りだけ | すべての操作を自分で確認したい。慎重に扱いたい作業 |
| `acceptEdits` | Accept edits（VS Code では Edit automatically） | 読み取り、ファイルの編集、よく使うファイル操作のコマンド（`mkdir`、`touch`、`mv`、`cp` など） | 変更内容は、あとでまとめて確認する |
| `plan` | Plan | 読み取り。ファイルは編集しない | 変更する前に、調査と計画だけをさせたい |
| `auto` | Auto | すべて。ただし、分類器が、裏で操作を審査する | 時間のかかる作業。確認の多さを減らしたい |
| `dontAsk` | （ターミナル版だけ） | 作業フォルダーの中の読み取りと、あらかじめ許可した操作だけ。確認が必要になる操作は、確認せずに拒否する | 自動実行の仕組みの中で、決めた操作だけをさせたい |
| `bypassPermissions` | Bypass permissions | すべて | 外部から切り離されたコンテナーや仮想マシンの中だけ |

### acceptEdits：ファイルの編集は確認しない

ファイルの編集と、よく使うファイル操作のコマンドを、確認なしで実行します。対象は、作業フォルダーの中のパスだけです。それ以外のシェルのコマンド（ビルド、テスト、`git push` など）は、これまでどおり確認が出ます。

変更内容を、1 つずつその場で承認するのではなく、あとから差分でまとめて確認したいときに向いています。

### plan：調べて、計画を立てるだけ

Claude は、ファイルを読み、調査のためのコマンドを実行しますが、ファイルは編集しません。計画を示したところで止まり、利用者が計画を承認してから、実行に移ります。

### auto：分類器が、利用者の代わりに審査する

auto モードでは、日常的な確認が出なくなります。その代わりに、分類器と呼ばれる別のモデルが、操作を実行前に審査します。依頼された範囲を超える操作や、Claude が読んだ内容にそそのかされたように見える操作などは、分類器が止めます。

公式ドキュメントには、次の注意が書かれています。

- auto モードは確認を減らすが、**安全を保証するものではない**。方向性を信頼できる作業に使うもので、慎重に扱うべき操作での確認の代わりにはならない。
- 分類器が、続けて 3 回、または合計で 20 回、操作を止めると、auto モードは一時停止し、通常の確認に戻る。

auto モードを使える条件は、対応しているモデルであることと、組織の管理者が無効にしていないことです。

### bypassPermissions：確認を行わない

確認と安全のための検査を行わずに、操作をそのまま実行します。公式ドキュメントは、**外部から切り離されたコンテナーや仮想マシンの中だけで使う**ように、警告しています。普段の PC で確認を減らす目的には、使いません。

## モードの切り替え方と、始まるときのモード

セッションの途中で、いつでもモードを切り替えられます。

| 使う場所 | 切り替え方 |
|---|---|
| ターミナル版 | `Shift+Tab` を押すたびに、順番に切り替わる |
| デスクトップアプリ | 送信ボタンの横にある、モードの選択欄 |
| VS Code の拡張機能 | 入力欄の下にある、モードの表示をクリックする |

新しいセッションが、どのモードで始まるかは、使う場所ごとに決まり方が違います。

| 使う場所 | 始まるときのモードの決まり方 |
|---|---|
| ターミナル版 | ① 起動時の指定（`--permission-mode`）→ ② 設定ファイルの `permissions.defaultMode` → ③ 組み込みの既定値、の順で、最初に当てはまるもの。組み込みの既定値は、バージョン 2.1.283 以降では `auto` |
| デスクトップアプリ | 設定ファイルの `permissions.defaultMode` を読む。ただし、選択欄で選んだモードは、フォルダーごとに記憶され、`defaultMode` より優先される（Plan は、そのセッションだけ） |
| VS Code の拡張機能 | ① 拡張機能の設定 `claudeCode.initialPermissionMode` → ② 選択欄で最後に選んだモード → ③ 管理設定か `~/.claude/settings.json` の `permissions.defaultMode` → ④ 組み込みの既定値、の順。プロジェクトの `.claude/settings.json` は、始まるときのモードには使われない |

設定ファイルで、始まるときのモードを指定する例です。`~/.claude/settings.json` に、次のように書きます。

```json
{
  "permissions": {
    "defaultMode": "acceptEdits"
  }
}
```

1 つ、注意があります。`auto` と `bypassPermissions` は、プロジェクトの設定ファイル（`.claude/settings.json`、`.claude/settings.local.json`）に書いても、効きません。`auto` で始めたい場合は、利用者ごとの設定ファイル（`~/.claude/settings.json`）に書きます。

## 権限ルール

権限モードが全体の基準を決めるのに対して、権限ルールは、特定のツールやコマンドについて、個別に決めます。

| ルールの種類 | 働き |
|---|---|
| allow | 当てはまる操作を、確認なしで許可する |
| ask | 当てはまる操作のたびに、確認する |
| deny | 当てはまる操作を、禁止する |

### 評価の順番

ルールは、**deny、ask、allow の順**に調べられ、最初に当てはまったものが結果になります。ルールの細かさは、順番に影響しません。

このため、広い deny ルールの中に、allow ルールで例外を作ることはできません。たとえば、`Bash(aws *)` を deny にすると、`Bash(aws s3 ls)` を allow に書いても、禁止されたままです。

もう 1 つ、大切な点があります。権限ルールを守らせているのは、モデルではなく、Claude Code の本体です。会話の中の指示や `CLAUDE.md` に「このコマンドは実行しないで」と書くことは、Claude の行動の方針にはなりますが、実行を止める仕組みにはなりません。確実に止めたい操作は、deny ルールに書きます。

### 書き方

ルールは、`ツール名` または `ツール名(条件)` の形で書きます。設定ファイルでは、次のようになります。

```json
{
  "permissions": {
    "allow": [
      "Bash(npm run *)",
      "Bash(git commit *)"
    ],
    "deny": [
      "Bash(git push *)"
    ]
  }
}
```

この例では、npm のスクリプトの実行と `git commit` は確認なしで実行され、`git push` で始まるコマンドは禁止されます。

シェルのコマンドのルールでは、`*` が「任意の文字列」を表します。

| ルール | 当てはまる | 当てはまらない |
|---|---|---|
| `Bash(npm run build)` | `npm run build` | `npm run build --watch` |
| `Bash(npm run *)` | `npm run build`、`npm run test --watch` | `npm install` |
| `Bash(ls *)` | `ls -la`、`ls` | `lsof` |
| `Bash(ls*)` | `ls -la`、`lsof` | |

書くときの注意は、次のとおりです。

- **`*` は、サブコマンドのあとに置く。** `Bash(git log *)` は `git log` だけを許可するが、`Bash(git *)` は、git のすべてのコマンドを許可してしまう。
- **`&&` などでつないだコマンドは、それぞれが調べられる。** `Bash(safe-cmd *)` を許可しても、`safe-cmd && other-cmd` の `other-cmd` は、許可されない。
- **ファイルの読み書きは、`Read(パス)` と `Edit(パス)` で書く。** たとえば、`Read(./.env)` を deny にすると、そのファイルを Claude のファイル用のツールで読めなくなる。

ルールの書き方には、ほかにも細かい決まりがあります。設定ファイルの置き場所と優先順位とあわせて、「04. 設定ファイルの仕組み」で扱う予定です。

### 確認の画面からルールを保存する

確認の画面には、「はい」「いいえ」のほかに、「はい、今後は確認しない」にあたる選択肢が出ることがあります。これを選ぶと、その操作についての allow ルールが、自動で保存されます。

| 操作の種類 | 「今後は確認しない」を選んだときの有効な範囲 |
|---|---|
| シェルのコマンド | そのリポジトリと、そのコマンドについて、以後ずっと |
| ファイルの変更 | そのセッションが終わるまで |
| Web ページの取得 | そのリポジトリと、そのドメインについて、以後ずっと |

ずっと有効になるルールは、リポジトリの `.claude/settings.local.json` に保存されます。このファイルは、自分だけの設定を置く場所です。

確認の画面に、この選択肢が出ないこともあります。その場合は、その場で 1 回だけ承認するか、ルールを自分で設定ファイルに書きます。

## 作業フォルダー

Claude は、既定では、セッションを始めたフォルダーの中のファイルに、アクセスできます。このフォルダーを、作業フォルダーと呼びます。作業フォルダーの中の読み取りには、確認が出ません。

作業フォルダーの外のファイルを読もうとすると、確認が出ます。別のフォルダーも日常的に使う場合は、作業フォルダーを追加できます。

| 追加する方法 | 内容 |
|---|---|
| 起動時 | ターミナル版で、`--add-dir <パス>` を付けて起動する |
| セッションの途中 | `/add-dir` コマンドを使う |
| 設定として残す | 設定ファイルの `additionalDirectories` に書く |

追加したフォルダーは、元の作業フォルダーと同じ扱いになります。読み取りは確認なしで、編集は、そのときの権限モードに従います。

## 確認が多く出るときの、原因と減らし方

確認が多いと感じたときは、**どの種類の操作で確認が出ているか**を見ると、原因を絞り込めます。

| 確認が出ている操作 | 考えられる原因 | 減らし方 |
|---|---|---|
| ファイルの編集のたびに出る | モードが Manual になっている | Accept edits に切り替える |
| ビルドやテストなど、同じコマンドで毎回出る | そのコマンドの allow ルールがない | 確認の画面で「今後は確認しない」を選ぶ。または、`permissions.allow` に、そのコマンドのルールを書く |
| 作業フォルダーの外のファイルを読むときに出る | そのフォルダーが、作業フォルダーに含まれていない | 作業フォルダーに追加する。または、そのフォルダーでセッションを始める |
| どのコマンドでも出る | モードが Manual で、ルールもない | Auto に切り替える。または、よく使うコマンドを allow ルールにまとめて書く |
| 新しいセッションを始めるたびに、Manual に戻る | 始まるときのモードが Manual に決まっている | `permissions.defaultMode` を設定する。VS Code の拡張機能では、拡張機能の設定も確かめる |
| allow ルールを書いたのに出る | ask ルールや deny ルールが先に当てはまっている。`&&` でつないだ別のコマンドが、ルールに当てはまっていない。ルールの `*` の位置が合っていない | ルールの一覧を確かめる。ターミナル版では `/permissions` で、すべてのルールと、それぞれが書かれているファイルを見られる |
| `.git` や `.claude` の中への書き込みで出る | 保護されたパスである | 仕様。allow ルールでは、あらかじめ許可できない |
| Auto を選べない | モデルが対応していない。または、組織の管理設定で無効になっている | 利用者の側では変えられない場合がある（下の「組織の設定による制限」を参照） |

### 減らし方の選び方

確認を減らす方法は、大きく 3 つあります。安全さと手間のつり合いが、それぞれ違います。

| 方法 | 確認の減り方 | 気をつける点 |
|---|---|---|
| allow ルールを足していく | 許可したコマンドだけ、出なくなる | 何を許可したかが、はっきりしている。`*` を広く書きすぎない |
| Accept edits にする | ファイルの編集で、出なくなる | コマンドの確認は残る。変更内容は、あとで差分を確認する |
| Auto にする | 日常的な確認が、ほぼ出なくなる | 分類器の審査は、安全の保証ではない。方向性を信頼できる作業に使う |

これらは、組み合わせて使えます。たとえば、「Accept edits にして、ビルドとテストのコマンドだけを allow ルールに書き、`git push` は ask ルールにして毎回確認する」という設定ができます。外部に影響する操作（公開、送信、削除など）は、確認を残しておくのが安全です。

## どの設定にしても、確認が残る操作

次の操作は、どのモードでも、自動では許可されません。

- **ask ルールに当てはまる操作**：auto モードでも、確認が出る。
- **保護されたパスへの書き込み**：`.git`、`.vscode`、`.claude` などへの書き込みは、Manual と Accept edits では確認が出て、Auto では分類器の審査に回る。allow ルールでは、あらかじめ許可できない。リポジトリの状態や、Claude 自身の設定を、誤って壊さないための仕組み。
- **利用者への質問**：Claude が、選択肢を示して利用者に尋ねる操作は、確認そのものが目的なので、省略されない。
- **重要なパスの削除**：`rm -rf /` や `rm -rf ~` のような削除は、allow ルールでは許可されない。

## 組織の設定による制限

組織で Claude Code を使う場合、管理者が、管理設定を配布していることがあります。配布の方法は、PC の中に置く設定ファイル、端末を管理する仕組み、管理者用の画面からの配信など、いくつかあります。管理設定は、利用者やプロジェクトの設定より優先され、上書きできません。権限に関係するものには、次のような設定があります。

| 管理設定の項目 | 働き |
|---|---|
| `permissions.disableAutoMode` | auto モードを使えなくする |
| `permissions.disableBypassPermissionsMode` | bypassPermissions モードを使えなくする |
| `permissions.defaultMode` | 始まるときのモードを指定する |
| `allowManagedPermissionRulesOnly` | 権限ルールを、管理設定に書かれたものだけにする。利用者やプロジェクトが書いたルールは、使われなくなる |
| 管理設定の中の deny ルール | どの設定でも、上書きできない |

自分で設定を変えても確認が減らないときは、管理設定で制限されている可能性があります。その場合は、利用者の側では変えられないので、管理者に確認します。

## 実際にやってみる

このサイトの作業で使っているセッションが、どの設定で動いているかを確かめました。

### 今のセッションの権限モードを確かめる

デスクトップアプリが Claude Code を起動するときの指定は、実行中のプロセスの一覧で見られます。

```bash
ps -axo command | grep 'claude-code' | grep -o -- '--permission-mode=[a-z]*'
```

結果は、次のとおりでした。

```text
--permission-mode=auto
```

このセッションは、auto モードで始まっていました。

### 権限ルールが、どこかに書かれているかを確かめる

権限ルールが書かれる場所を、順に確かめました。

| 場所 | 役割 | 結果 |
|---|---|---|
| `~/.claude/settings.json` | 利用者ごとの設定 | ファイルがない |
| プロジェクトの `.claude/settings.json` | プロジェクトで共有する設定 | ファイルがない |
| プロジェクトの `.claude/settings.local.json` | 自分だけの設定。「今後は確認しない」の保存先 | ファイルがない |

利用者とプロジェクトの設定には、権限ルールは 1 つも書かれていませんでした。

### 分かったこと

このサイトでは、ページを書く、ビルドする、コミットする、公開する、という作業を、確認がほとんど出ない状態で進めています。その理由は、allow ルールを書いているからではなく、**auto モードで動いているから**でした。

このことから、確認の出方が環境によって違うときに、最初に確かめることが分かります。

1. そのセッションが、どの権限モードで動いているか
2. 権限ルールが、どのファイルに、何と書かれているか
3. 管理設定があるか

## まとめ

- 確認が出るかどうかは、操作の種類、権限モード、権限ルールの 3 つで決まる。
- 読み取りと、読み取り専用のコマンドは、確認なしで実行される。ファイルの変更と、それ以外のコマンドは、Manual では確認が出る。
- 権限モードは 6 つある。普段の作業で確認を減らすために使うのは、Accept edits と Auto。bypassPermissions は、切り離された環境だけで使う。
- 権限ルールは、deny、ask、allow の順に調べられる。deny は、ほかの設定では上書きできない。確実に止めたい操作は、指示ではなく、deny ルールに書く。
- 確認が多いときは、どの種類の操作で出ているかを見て、モードの変更、allow ルールの追加、作業フォルダーの追加のどれが合うかを選ぶ。
- 保護されたパスへの書き込みなど、どの設定でも確認が残る操作がある。組織の管理設定で、制限されていることもある。
